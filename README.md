面向「快速上线 + 用户增长」的微信小游戏工程骨架。**零构建步骤**,用微信开发者工具直接导入本目录即可运行。

## 一、三步跑起来

### 1. 导入项目
微信开发者工具 → 导入项目 → 选择**本目录** → 填入自己的小游戏 AppID(把 `project.config.json` 里的 `wx0000000000000000` 换成真实 AppID)。

### 2. 开通云开发
工具顶部「云开发」→ 开通 → 复制**环境 ID**(形如 `xxx-1a2b3c`),写入 `js/config/config.js`:

```js
CLOUD_ENV: '这里换成你的环境 ID',
```

> 如果暂时不想接云开发,把 `ENABLE_CLOUD` 设为 `false`,游戏会以纯单机模式运行(登录走游客态、分数只存本地),玩法开发完全不受影响。

### 3. 部署云函数
在工具左侧文件树中,右键 `cloudfunctions/` 下的每个函数目录 → **上传并部署:云端安装依赖**。共 5 个:

```
login  submitScore  getRank  saveArchive  dailySign
```

部署完成后点击「编译」,即可看到完整闭环:**启动 → 静默登录 → 主页 → 开局 → 结算上榜 → 分享 → 排行榜**。

## 二、云开发数据库配置(必做)

在「云开发 → 数据库」中按下表创建集合,并设置**权限**与**索引**。
权限设置至关重要:默认权限过宽会导致任何人可读写他人数据。

> **收口版只需前 5 个**(`users` `user_stats` `scores` `archives` `configs`)。
> `sign_logs` / `events` 分别服务于已砍掉的签到玩法与埋点分析,**本项目不创建也不影响运行**。

| 集合 | 权限设置 | 必须创建的索引 |
|---|---|---|
| `users` | 仅创建者可读写 | `_openid`(唯一) |
| `user_stats` | 所有人可读,仅创建者可写 | `bestScore` 降序 + `updatedAt` 升序(复合);`_openid`(唯一) |
| `scores` | 仅创建者可读写 | `_openid` + `createdAt` 降序(复合) |
| `archives` | 仅创建者可读写 | `_openid`(唯一) |
| `sign_logs` | 仅创建者可读写 | `_openid` + `date`(**复合唯一**,幂等依赖它) |
| `configs` | 所有人可读,仅管理端可写 | `key`(唯一) |
| `events` | 仅管理端可写 | `_openid` + `ts` 降序 |

> `sign_logs` 的复合唯一索引是签到幂等的最后一道保障 —— **不建索引,并发下会重复发奖**。(收口版未启用签到,此条仅作留存说明。)

`configs` 集合用于远程开关(改配置不用重新提审)。写入示例:

```json
{ "key": "DISABLE_RANK", "value": false }
```

## 四、当前玩法:竖版躲障跑酷 ——「红色的躲,金色的抢,边缘的险」

单指左右拖动,场上同时有两种东西要处理,而且它们的要求**正好相反**:

（下表是**经典模式**的数值。其余三个模式的数值覆盖见 §五。）

| 元素 | 造型 | 你要做的事 | 结果 |
|---|---|---|---|
| **红色障碍** | 方形 | 躲开 | 撞到扣 1 条命 + 无敌 1.2 秒;成功躲过 **+5 分** |
| **金色能量块** | 圆形 | **主动撞上去** | 命未满回 1 条命(本局上限 2 次);命已满 **+8 分** |
| **擦身而过** | 贴着红块边缘掠过 | **越近越好** | 每个红块限一次,**+2 分** |

> **设计意图**:纯躲避是"避免坏事"(负反馈),玩久了只有压力没有爽点。
> 加入"要抢的东西"之后,同一个道具在**受伤时**和**满血时**价值不同,
> 于是产生"为了回命,值不值得往红块边上冲"的取舍 —— 这就是本作的心流来源。
> 擦身而过则是第二条线:它把"安全躲避"(5 分)和"贴身掠过"(7 分)分出了收益差,
> 于是"贪"不再只在金块出现时才需要判断,而是每一次躲避都在做判断。

金色能量块有 **55%** 的概率**贴着刚生成的红块**出现(横向间距 110–190),想拿就得往危险边上靠。

难度随存活时间递增:下落速度 380 → 900,生成间隔 0.95s → 0.45s。

**计分公式**:`分数 = 存活秒数 × 10 + 躲避红块次数 × 5 + 擦身而过次数 × 2 + 命满时拾取金块的累计加分`

> 上面三个数值（速度区间、生成间隔、计分权重）都是**经典模式的基准值**，写死在
> `config.GAME`。另外三个模式通过 `Modes.paramsOf()` 做**参数覆盖**得到自己的数值 ——
> 覆盖表在 `js/gameplay/modes.js`，见 §五。

### 留人设计

留存 = **会话局数 × 回访理由**。两者是乘法关系,所以分开补。

**(1) 单局层:降低摩擦、加密反馈** —— 全在 `game-scene.js`,不动玩法规则

| 手段 | 做法 | 为什么 |
|---|---|---|
| **降低重开摩擦** | 结算后点击面板上半区任意位置立即重开(死亡后 0.9s 解锁) | 一局 30 秒的游戏,"再来一局"多一次点击的摩擦,乘上几十局就是巨大流失 |
| **近失提示** | 差一点点破纪录时,结算面板直接写"就差 N 分破纪录!" | 比干巴巴的"历史最高 XXXX"更能催出下一局 |
| **即时反馈** | 擦身 / 拾取都有飘字 + 整屏金边闪 | 躲障类正反馈天然稀疏,不补的话体感就是"一直在等难度涨上来" |

**(2) 跨局层:让"我在变强"被看见** —— 新增的成长系统,见下一节

**(3) 回访层:明天为什么再来** —— 独立签到页(**7 天周期**日历 + 累计里程碑) + 每日首局

> 回访层是三层里唯一需要"持续运营"的,所以刻意做得最薄:
> **只做签到,不做每日任务链、不做限时活动**。后者需要天天维护,和维护工期冲突。

签到的奖励曲线有两层,分别解决两个不同的问题:

| 层 | 规则 | 解决什么 |
|---|---|---|
| **7 天周期** | 第 1 格 100 金币,每格 +20,**第 7 格额外 +200**(单格 320);走完回绕到第 1 格 | "明天再来" —— 断签会重置周期,所以有回访压力 |
| **累计里程碑** | 累计签到 **3 / 7 / 14 / 30** 天,一次性发 **100 / 200 / 400 / 800** 金币(不要求连续) | "这周/这个月再来" —— 周期之上再挂一层长期钩子 |

一轮周期合计 **1320** 金币(日均 189),不足以买下中高档皮肤(1680~2450),所以签到是"
补贴"而不是"主要收入" —— 主力仍然是局内表现。断签不清空**累计天数**,只重置**这一轮周期**。

## 五、玩法模式、特效与界面规范

### 5.1 每个模式一个独有机制（而不是只调数值）

四个模式共用**同一套规则骨架**（生成 → 下落 → 碰撞 → 计分），差异收在一份**纯数据**里
（`js/gameplay/modes.js`）。`rules.js` 只负责"照着这组参数跑"。

> 为什么不给每个模式写一份 `rules.js`？四个文件会迅速漂移成四份要同步维护的代码 ——
> 改一个碰撞 bug 要改四遍，还必然漏一遍。收成纯数据之后，**加第五个模式的代码成本接近于零**。

**但"只调数值"这条路走不通 —— 这是本轮最大的一个认知修正。**

一开始四个模式其实只是"同一套规则 + 四组不同数值"：都是左右拖动躲红块，只是更快、
金块更多、限时更短。结果就是**玩家从头到尾做的动作一模一样，只是快慢不同** ——
体感上"四个模式太像了"。数值差距拉到极端也治不了：把速度调到两倍，玩家做的事还是那一件。

所以改成 **每个模式一个彼此正交的独有机制**，各自改动玩家决策里**不同的那一维**：

| 模式 | 独有机制 | 改的是哪一维 | 玩家做的判断变了 | 入榜 |
|---|---|---|---|---|
| **经典** | *（一个都不开）* | 基准 / 尺子 | 三种要素齐全，是其余三个模式的比较基准 | ✅ |
| **疾风** | **障碍横向摆动** `OBSTACLE_SWAY` | **怎么躲** | 读单个块的波形去预判落点 —— **避** | ❌ |
| **金潮** | **连击链 + 金块游走** `COMBO_*` / `PICKUP_DRIFT` | **为什么贪** | 金块会跑，要算落点提前站位 —— **追** | ❌ |
| **死线** | **走廊收窄 + 左右摇摆** `LANE_*` | **空间有多大** | 跟着整个空间的节拍走 —— **随** | ❌ |

三条轴改的是**三件不同的事**（躲的方式 / 贪的理由 / 空间的大小），所以四个模式不再是
"快慢不同的同一件事"。四个模式加机制前的经典行为**逐字节不变** —— 三条机制的默认值一律
"完全不生效"（振幅 `0` / `COMBO_ENABLED: false`、倍率上限 `1` / 不游走 / 不收窄 / 不摇摆），详见 §5.2。

**★ 第二轮修正：机制必须是"看得见的运动"，不能只是一个数字。**

第一版的「金潮 = 连击倍率」「死线 = 走廊线性收窄」都输在同一点上：
**倍率是一个看不见的倍数；而收窄 55 秒才走完 34%，玩家几乎察觉不到。**
两者的问题一模一样 —— **玩家的动作其实没有变**。于是给它们各补一层物理上可见的运动：

- 金潮的金块**自己横向游走**（匀速直线 + 边界折返），速度 = 基础值 × **当前倍率** ——
  倍率于是同时成了"奖励刻度"和"难度刻度"：**越贪越难追**。
  规则可以一句话说完：**只要你动，就追得上；你不动，一个也拿不到。**（与疾风"不动会被撞"正好镜像）
- 死线的走廊**一边收窄一边整体左右平移**，幅度随收窄进度增长（越到后面荡得越急），
  周期恒定 5 秒一个来回。空间从静止的背景，变成了一个要应付的东西。

现在三条机制的玩家动作分别落在 **避 / 追 / 随** 上，彼此再也不可能混淆。

> 这一版的判断值得单独记：**机制的可感知性 ≠ 机制的强度。**
> 一个数值上很强的机制（倍率 ×3）如果玩家看不见，体感上就等于不存在；
> 一个数值上很弱的机制（走廊挪 110 像素）只要动起来，玩家立刻就能懂。
> 另外，这两条机制加完**服务端一行都没改** —— 金块的**数量**没变（游走只让它更难拿），
> 走廊的**生成间隔**也没变（摇摆只让空间移动），所以上限表 `32/47/49/48` 原封不动。

**几个必须记住的设计判断：**

- **摆动由纵向位置 `y` 驱动，不由时间驱动。** 若由时间驱动，速度越快能看到的波形越少，
  "预判"就退化成运气；用 `y` 驱动后无论多快，玩家看到的永远是**同一段完整波形** —— 可学、可预判。
  振幅 96 ≈ 一个红块的半个身位，波长约 700 像素（屏高约 1334），所以每块红块在屏内会完整地
  荡将近**两个来回**：少于一个来回玩家还没读出方向块就过去了，多于三个来回就成了无规律的抖动。
- **每块红块的摆动相位随机。** 相位相同的话整屏会一起左右平移，玩家一眼就读完了，机制等于白做。
  生成范围还要**预先扣掉振幅**，否则块会荡到屏幕外。
- **金块游走用匀速直线，不用正弦。** 匀速是全作最好读的运动 —— 玩家一眼就能看出它往哪跑、
  提前站到它的必经之路上；而"摆动"要读波形、"摇摆"要跟节拍，三种运动**要动脑的地方刻意不同**。
  基础速度 150 px/s 远低于玩家拖动的速度（千级以上）；连满倍率时 450 px/s 才刚进入"必须提前起跑"。
- **走廊摇摆的振幅写在几何安全区里**：`amp = min(LANE_SWAY, full×(1−minRatio)) × 收窄进度`，
  而 `LANE_SWAY(110) ≤ 375×(1−0.66) = 127.5` —— 走廊**永远不会被推出屏幕**。
  这条约束写在公式里，不靠运行时兜底夹取；`test-modes.js` 会断言它。
- **收窄停在 66%，而且收到底就停。** 走廊最窄 750×0.66 = 495，减最宽红块 280 还剩 **215**，
  刚好够玩家（宽 96）挤过去；再窄就从"有难度"变成"无解"。停在固定值才有**终点感**，
  否则最后几秒会变成持续的不安。宽度确定之后，摇摆就是最后那段的主戏。
- **连击模式里被撞不扣分，只把倍率打回原点。** 失去的是"接下来每个金块多拿一倍"的预期，
  比扣已到手的分数更想补回来。而断链本身是**沉默的**，必须显式飘字说出来。
- `mechanicOf(def)` 的机制标签（`限时 / 摆动 / 追猎 / 摇摆`）是**从实际参数派生**的，
  与"规则速览由实际参数生成"是同一条纪律 —— 手写文案迟早会和参数打起来，
  于是"界面写着摆动、其实没开"这类错永远不可能出现。
  （`追猎` 与 `连击`、`摇摆` 与 `收窄` 都是**二选一**：前者是后者"看得见的形态"，
  两个都报会变成一串没人会读的长词。）

**顺带保留的两处数值补偿**（它们不是独有机制，但少了就不公平）：

- **速度补偿**：疾风速度翻倍后若擦身判定窗口不变，"贴边"就从技巧变成运气；
  所以窗口 26 → 36。加了摆动之后这条**更必要** —— 块会主动向你扫过来。
- **收益与风险同步放大**：金潮金块变多的同时，贴着红块生成的概率也提高了（55% → 70%，
  间距上限 190 → 165）。否则这个模式只是"变简单了"，而不是"变得更贪了"。

### 5.2 只有经典计入全服榜，纪录按模式分开记

跨模式比分数是不公平的：死线模式 60 秒封顶，永远赢不了无限时长的经典。把不可比的分数
放在同一张榜上，榜就失去了"我在同类玩家中排第几"这个唯一的意义。

- 服务端 `MODE_LIMITS` 表按模式校验（见 §七 的警告），**只有 `scoreboard: true` 的模式才写 `user_stats`**；
  其余模式仍然往 `scores` 表记一条，只是不参与榜单排序。
- 客户端结算面板对非入榜模式**明说"不计入全服榜"**，而不是偷偷显示一个会被误读的名次。
- 纪录存 `bestByMode`（`{ 模式id: 最高分 }`）而不是共用一个 `bestScore` ——
  否则三个模式永远刷不出"新纪录"，玩家做对了一切却得不到任何确认。
- 近失提示（"就差 N 分破纪录"）的**基准也是本模式的纪录**：拿死线的 2000 分去比经典的
  5000 分，玩家永远只看到"差 3000 分"，那不是激励，那是一句"你不该玩这个模式"。

> ⚠️ **每个模式的 `maxScorePerSecond` 是服务端防作弊的唯一依据**，必须与
> `cloudfunctions/submitScore/index.js` 的 `MODE_LIMITS` 表**逐值一致**。
> 上限推导见 `Modes.rateOf()`（四项得分的每秒上限之和；金潮的拾取项要把 `COMBO_MAX` 乘进去）：
> 经典 30.56 → 32（余量 4.7%）/ 疾风 45.33 → 47（3.7%）/ **金潮 46.45 → 49**（5.5%）/ 死线 46.02 → 48（4.3%）。
> `test-modes.js` 会断言"上限 ≥ 推导值"且"余量在 0%~15% 之间"、"四个上限互不相同"，
> 让"改了参数忘了改上限"当场暴露。

> ⚠️ **机制开关的默认值（`config.GAME` 末尾）任何一端都不许改。**
> 它们必须是"完全不生效"（`OBSTACLE_SWAY: 0` / `COMBO_ENABLED: false` + `COMBO_MAX: 1` +
> `PICKUP_DRIFT: 0` / `LANE_SHRINK_SECONDS: 0` + `LANE_MIN_RATIO: 1` + `LANE_SWAY: 0`）。
> 因为**经典模式一条机制都不开**，它是所有比较的**基准**；
> 默认值一旦动了，"经典行为与加机制之前逐字节一致"这条地基就塌了。
> `test-modes.js` 会逐条断言这些默认值，`check-preview.js` 会比对两端逐值一致。

### 5.3 规则速览由**本模式实际参数**生成

READY 面板上的那几行字不是写死的文案，而是 `buildRuleText()` 从 `mode.params` 现算的。
**第 1 行永远是本模式独有机制的说明**（机制优先于数值 —— 玩家记不住"速度 520、间隔 0.72"，
但一定记得住"红块会摆"）：

```
经典  /  标准节奏，难度平滑上升
      金块回命(上限 2 次)，命满则 +8 分
      贴边掠过「险 +2」· 判定窗口 26

疾风  /  ★ 红块边走边左右摆动 —— 看清波形再动,站定必被扫到
      读着波形再动,考点从手速变成了预判
      金块回命(上限 2 次)，命满则 +6 分
      贴边掠过「险 +3」· 判定窗口 36

金潮  /  ★ 金块会横向游走,连击越高跑得越快 —— 站着不动,一个也拿不到
      目标不是活得久,而是别断链 —— 而且你得追得上
      金块回命(上限 3 次)，命满则 +6 分
      贴边掠过「险 +2」· 判定窗口 26

死线  /  ★ 限时 60 秒,活动走廊一边收窄一边左右摇摆
      时间在少,地方一边变小一边漂移 —— 没有喘息
      金块回命(上限 2 次)，命满则 +10 分
      贴边掠过「险 +3」· 判定窗口 30
```

（经典**一条机制都不开**，所以它没有那个 `★` 行 —— 这是刻意的，它是尺子。
金潮和死线的第一行都同时说清了两件事：**机制是什么**（游走 / 摇摆）与**它逼你做什么**（追 / 跟）。）

HUD 同样按实际参数画，而不是写死：

- 命数槽位数按 `world.params.LIVES`；
- 模式徽标上的文字 = 模式名 + **从参数派生的机制标签**（`疾风 · 摆动`）；
- 有连击的模式多一栏**连击读数**（`连 N　倍率 ×M` / `连击未开始`），限时模式把角落那格
  换成**倒计时**并补一条时间条。

这样"界面写着 2 条命、实际跑 3 条命""界面写着摆动、其实没开"这类**只有真机上才发现的错**
永远不可能出现。

### 5.4 特效层：`js/framework/effects.js`

四条硬约束，都是为了在低端机上不掉帧：

| 约束 | 做法 | 为什么 |
|---|---|---|
| **固定容量粒子池** | `MAX_PARTICLES = 220`，启动时一次性分配；池满**静默丢弃** | 特效丢一帧没人看得出，一次 GC 卡顿所有人都能感觉到 |
| **禁止 `shadowBlur`** | 发光用 alpha 叠加同心圆近似 | `shadowBlur` 是逐像素卷积，低端机上极贵 |
| **零状态环境层** | `ambient()` 是纯函数（位置 = `hash(i)` 与时间的函数） | 不占粒子池、零 GC；`parallaxX` 让背景粒子相对玩家反向位移，否则背景就是一张贴纸 |
| **swap-remove 回收** | `pool[n-1]` 换到被淘汰位置再收缩 `n` | 比 `splice` 便宜得多 |

API：`burst`（环形爆发）· `ring`（冲击波圆环）· `spark`（定向火花，方向即速度方向）·
`confetti`（破纪录彩带）· `update` / `render` / `clear` / `count` / `ambient`。

什么时候放哪种特效，都是**为了让一个机制被读懂**，不是为了好看：

| 事件 | 特效 | 为什么是这一种 |
|---|---|---|
| 受击 | 红色冲击波 + 方形碎片 | 两件一起放才有"撞上了"的重量感：只有碎片像散落的像素，只有圆环像一段 UI 动画 |
| 擦身 | 金色定向火花，方向 = **移动方向的反面** | "我从哪边擦过去的"被直接画出来，不用玩家去读飘字 |
| 拾取 | 爆发 + 小冲击波；回命用品牌绿、加分用金 | 两种结果用两种颜色，不用读字就知道刚才发生了什么 |
| **时间到**（仅死线） | 白色冲击波 + 向上飘的碎屑 | 刻意和"被撞爆"的红完全区分开 —— 结局不同，反馈就该不同 |
| **破纪录** | 彩带 | 全程唯一一次"庆祝"，值得给足 |

> ⚠️ 特效**只读不写**：永远不改 `world` 里任何数字。一旦特效开始影响判定，
> "看起来躲开了"和"真的躲开了"就会分家。

> ⚠️ 粒子分**两处**渲染：游玩中的粒子画在世界层之上、HUD 之下（它属于"场景里发生的事"）；
> 结算 / 准备态的粒子画在遮罩**之上** —— 破纪录彩带必须能飘过黑幕，
> 否则最该被看见的那一次庆祝会被结算面板压住。

### 5.5 模式选择放在主页，横排 chip

模式是**高频、低决策成本**的选择（四个选项，选中即生效），所以没有为它单开一层导航 ——
那等于每次开局多两次点击。横排 chip 让"换模式"和"开始游戏"共处一屏，
每个 chip 里三行：模式名 + **本模式独有机制的标签** + **该模式自己的最高分**（无记录显示 `—`）。
中间那行机制标签是玩家**在开局前**唯一能看出"四个模式不一样"的地方，所以必须显眼
（比如 `摆动` / `追猎` / `限时 · 摇摆`；经典显示 `基准`，因为它是尺子）。

> 主页下半部分**全部以屏幕底部为锚**（`bottom() + dy`）：不同机型的设计高度差异很大
> （16:9 → 1334、21:9 → 1750），底部锚定让这一整块在长屏上自然下移、留白落在中间。
> 布局表在 `home-scene.js` 顶部的 `L`，与预览页的 `HOME_LAYOUT` 逐值一致（`check-preview.js` 会比对）。

### 5.6 界面统一规范层：`js/framework/ui.js`

各场景（主页 / 游戏 / 商城 / 签到 / 排行榜）的界面一开始是分开写的，结果是"每张卡片都差一点点"：
圆角 12 或 16、间距 16 或 20、字号 23 或 26 —— **单看都还行，拼在一起就散**。
所以抽出一个**设计规范层**，把"一次性数值"全部消灭。
（这一层和 §5.7 的排版语言层是 `ui.js` 里紧挨着的两节：**这一节管"所有数值来自同一处"，
下一节管"文字不该只是一行文字"**。）

**四组 token（约定：场景里不再出现 17、23、46 这类随手写的数字）**

| token | 取值 | 用途 |
|---|---|---|
| `SPACE` | `xs 8 / sm 12 / md 16 / lg 24 / xl 32 / xxl 48` | 所有间距 |
| `RADIUS` | `sm 12 / md 18 / lg 26 / xl 34` | 所有圆角 |
| `TYPE` | `hero 92 / title 46 / heading 34 / body 28 / label 24 / caption 21 / eyebrow 20 / micro 17` | 所有字号（后两档见 §5.7） |
| `Ease` | `outCubic / outBack / inOutCubic` | 所有缓动 |

**五个绘制原语**

| 原语 | 做什么 | 关键的实现细节 |
|---|---|---|
| `bg(ctx,w,h,opt)` | 渐变背景 + 一层网格 | **缓存 `CanvasGradient`**（每帧只是一次 `fillRect`）；`opt.tint` 让每页顶部染一抹自己的主题色；`opt.grid:false` 关掉网格（游戏内场地元素多，再铺网格就乱了） |
| `card(...)` | 圆角 + 描边 + 顶部内高光；可选 `glow` | `glow` = 多层同心描边近似发光；`strokeWidth` 可配 |
| `pill(...)` | 药丸形 | 就是"半径 = 半高的 `card`"，保证和卡片同一种圆角关系 |
| `divider(...)` | 两端淡出的渐隐线 | 缓存渐变；直接用纯色线会显得"生硬地断在屏幕边缘" |
| `sheen(...)` | 给套不进 `card` 的形状就地补高光 | 商城皮肤卡、签到格这种形状特殊的地方用 |

**深色界面"一片死黑"的解法**：`COLORS` 补了**背景渐变两端**（`bgTop/bgBottom`）、
**三层表面**（`surface` / `surfaceHi` / `surfaceSunken`）、**两级描边**（`stroke` / `strokeHi`）
以及四个语义色的**亮一档变体**（`brandLight` / `accentLight` / `goldLight` / `dangerLight`）。
这样"背景 / 卡片 / 悬浮态"在明度上有了先后关系，界面才立得起来。
（**老键的值一字未改**，所以旧代码的观感不会跳动。）

**六个页面不该是同一块黑。** 此前六个场景共用一条 `#18202b → #0d131a` 的纵向渐变 ——
单独看没问题，连着切几页就会发现"每页都是同一块黑"，而且只有明度变化，
没有任何"光照方向"或"材质"的信息。这正是"黑色有点单调"的来源。改法是：

1. **光晕并进主渐变的色标里**，不另起一层径向渐变 —— 顶部先染一抹该页的主题色
   （`bgTop` 混 24% 的 tint），22% 处回落到中性，底部再压暗一档。
   视觉上得到"光从上方来"，而成本仍然是**一次全屏 `fillRect`，与改动前完全一样**。
   每页的 tint 分别是：主页/启动 `brand`、商城/签到 `gold`、排行榜 `accent`、游戏内 `mode.color`。
2. **一层 2% 白的网格**（间距 112，十几条 1px `fillRect`）—— 把"平面"变成"有尺度的空间"。
   2% 是在深色底上"看得到格子但读不出格子"的那一档；再明显一点就变成蓝图纸了。

> 为什么不让每个页面自己画背景：那会立刻漂成六套光照方向。
> **页面之间的差异只应该是色相，不该是光照逻辑。**

> **精致感真正的来源不是特效，而是三件小事**：统一圆角 + 1px 半透明描边 + 顶部一道内高光。
> 这三样最廉价，也最有效。
>
> **`shadowBlur` 一次都不用**（与 §5.4 特效层同一条禁令）—— 发光一律用 alpha 叠加的
> 同心描边 / 同心圆近似。
>
> **整屏只允许一处发光**：结算卡片破纪录时 `glow: gold`。"这局不一样"不需要文字强调，
> 让唯一的光点去说。处处发光 = 处处不发光。
>
> HUD 的分数用**描边**而不是固定宽度胶囊：分数位数 3~6 位不定，胶囊要么框不住要么太宽，
> 居中的大胶囊还必然和两侧的徽标 / 连击读数抢位置；描边没有宽度，位数再多也永远合适。

### 5.7 排版与图形语言层：把文字做成界面
`ui.js` 里紧挨着规范层的**另一节**，纯绘制、**不认识任何业务概念**
（`framework` 不该知道什么是"稀有度 / 模式 / 成就 / 榜单"）。

**为什么需要它。** 五个页面做完之后回头一看，问题不在字体，而在**文字周边的东西**：
所有文字几乎都是"一个 `fillText` 摆在某个坐标上"，**页面靠字号表意、不靠层级** ——
每一屏读起来都像一段说明文字，而不是一张被设计过的界面。缺的是区块标题、图标、分隔线、
单位、空状态、加载指示、头像这七样东西。

**量字三件套**

| 原语 | 做什么 | 关键的实现细节 |
|---|---|---|
| `measure(ctx, str, size, weight)` | 量一段文字的宽度 | ⚠️ **canvas 的 `font` 是全局态，量完必须把原来的字体还回去** —— 否则"量出来的宽"和"画出来的宽"会差一个字体。这类 bug 只在个别机型偶尔出现，极难查 |
| `fitText(...)` | 超宽就自动降字号，返回实际画出的宽 | 昵称、长文案用 |
| `ellipsis(str, n)` | 截断加省略号 | 副标题、说明文字用 |

**内容原语**

| 原语 | 做什么 | 为什么 |
|---|---|---|
| `section(ctx, o)` | 左主题色短竖条 + 标题 + 右侧附注 | **全作五个页面标题同一套语气** —— 玩家不用读字就知道自己在哪一页 |
| `stat(ctx, it)` | 图标 / 数值 / 单位 / 标签 四层 | **数值与单位必须一起居中**（各自居中会让一排数字左右不齐 —— "那一点点差异就是没做完的来源"） |
| `kv(ctx, o)` | 键值行 + 可选点线引导 | 详情、规则到处用 |
| `badge(ctx, o)` | 统一角标语言 | 榜单的「我」与签到格的「大奖」**共用同一套语言** |
| `empty(ctx, o)` | 图标 + 主文案 + **下一步该做什么** | 一句孤零零的灰字会让人以为页面坏了 |
| `spinner(ctx, o)` | 随时间旋转的弧 | **"在动"本身就是信息** —— 静态三个字分不清"在加载"和"卡住了" |
| `icon(ctx, name, ...)` | **14 个矢量图标**，全路径绘制、**笔画式** | 零美术资源；`lineWidth` 随 size 走，同一份代码在 18px 与 92px 下都成立 |
| `monogram(ctx, name, ...)` | 字母头像 | **色相由昵称哈希决定**（`hashCode()`）⇒ 同一个名字永远是同一个颜色；零美术资源、零服务端字段 |

`icon` 的 14 个名字：`coin / trophy / medal / crown / calendar / check / clock /
flame / lock / star / chart / gift / shapes / alert`。

**"数字语言"是一条统一纪律**：数值大、单位小两档，且**一起居中**。
应用于主页最高分、排行榜分数、签到连签天数、结算面板分数、签到达成浮层的金币、下一款造型的差额 ——
**一个 120px 的裸数字，玩家要自己想它是分数、金币还是名次。**

**三处结构升级**（都是"让一组信息读起来像一组"）：

1. **三张独立小卡 → 一条指标栏**（主页）：三个数字本来就同属一份进度，所以共用一张底 +
   两条竖分隔线。分隔线同时表达两件事 —— "这是三个独立指标"和"它们同属一组"。
2. **一行文字 → 一张带进度的小卡**（主页"下一款皮肤"）：左边画**下一款造型的 `sprite()` 小预览**，
   右边差额大数字，底部贴着下沿一条进度条。**目标如果只是一个名字，动力会少一半。**
3. **一串裸文字 → 卡片行**（排行榜）：榜单的信息结构天生是**表格**，而表格的可读性 100% 来自
   对齐、分隔与身份识别 —— 名次奖牌徽章 / 字母头像 / 昵称 + 角标 / **分数右对齐**
   （**左对齐的数字列比不出大小**）。

**还有两件"看起来小、其实是坑"的事**：

- **字体字符 → 矢量画法**：主页签到卡原来的右箭头是一个 `'›'` 字符。字体字符的字重、
  基线、左右边距**逐机型不同**，是"在开发机上好好的、在别人手机上歪了"的典型来源 ——
  换成两条 `lineTo`。
- **新增原语必须两端同名同序**：预览页是副本，少内联一个原语不是"长得不一样"，而是
  **ReferenceError、整个页面白屏**。`check-preview` 会把 17 个原语的名字逐一点名。

### 5.8 同屏信息不该说两遍（以及"文字重叠"到底怎么查）

"内容显得很挤/很乱"通常不是间距问题，而是**同一件事在一屏里说了好几遍**。
商城页就是一个实例：头部写 `已拥有 6 / 24`、同一行右端又写 `4%`、页签上还写着 `皮肤 6/24`
—— 同一件事说了三遍。玩家不会觉得"信息丰富"，只会觉得"这页没收拾干净"。
现在的分工是：**进度条自己说明比例、右端百分比说明进度、页签上的数字说明"这个列表有多少"**，
头部只留一个「收集进度」的标签。

> 判据很简单：**任何一个数字，在一屏里只该有一个家。**
> 出现第二个"家"时，先问它是不是在回答另一个问题；不是就删掉。

**"文字重叠"要用工具查，不能靠看代码。** 重叠是几何问题：一个坐标摆在
`safeTop + 372`、另一个摆在 `+376`，差 4 像素在代码里毫无异常，在屏幕上就是两行字压在一起。
本轮为此做了一套诊断探针（用法见 §八 自检清单），它逼出来的第一个真 bug 很值得记：

> **① `ui.text()` 的宽度曾经是在 `ctx.restore()` 之后量的。** canvas 的 `font` 是**全局态**，
> `restore()` 之后它已经变回调用前的字体了 —— 拿那个字体去 `measureText`，
> 量出来的宽度与刚画出来的那行字不是一个字号。
> 全作所有"文字 A 的右边接文字 B"的布局都吃这个返回值（最典型的是"数值 + 单位"一起居中），
> 于是签到页的「天」直接压在了大数字上。
>
> 它可怕的地方在于**不像 bug**：返回值是个正常数字，不报错、不抛异常，只是"差一点"；
> 而且差多少取决于"上一个 `ui.text` 用了多大的字"——今天看着好，明天换个数据就歪了。
> 现在 `check-preview` 有一条断言专门盯它（确认 `measureText` 在源码里出现在 `restore` 之前）。

**但"文字 ↔ 文字"只是重叠的一半 —— 另一半是"文字被图形的边切掉"。**
探针第一版只比文字与文字，于是商城头部那条真问题完全在它视野之外：
`装扮 · 成就` 被右侧的金币药丸切掉了"成就"两个字。它躲过判定有两个原因 ——
药丸是**图形**不是文字；而且药丸画在附注**之后**（是它压住了字，不是字压住了它）。
为此补了一条 **「压边」** 判定：文字盒与实心块（含**描边** —— 真正切字的就是那条金色描边）
**部分相交**才算；全在内（正常装在卡片里）与全在外都不算。三条约束把噪音压到零：

- **块必须画在文字之后**（块压在字上才算"压住"）。跑酷里每一帧都有红块/金块从 HUD 大字底下掠过，
  它们画在世界层、字画在 HUD 层 —— 文字在块**上面**时字是完整清晰的，玩家不会说"字重合了"。
- **压掉的必须是一条实质的带**（≥ 半个字高），否则就只是"字的下沿蹭到卡片上沿"那种 2~7px 的贴边。
- **每条文字只取包含比最大的那个块**（一张卡里还套着预览底板/顶部高光，逐块比对会刷屏）。

**它随后又抓出两个同类的真 bug，而且两个都不是"调参"能修的 —— 是几何依赖没建立：**

| 位置 | 原来是 | 根因 | 现在 |
|---|---|---|---|
| 商城头部标题 | `w: screen.width - 200`（写死"右侧留 200 够放药丸"） | 药丸宽度是 `max(146, 数字宽 + 52)`，**随金币位数变化**；0 金币时药丸左边缘 556、附注右端 598 ⇒ 切掉 42px | `w: pillX - 24 - 48`（跟着药丸实际左边缘收边） |
| 签到浮层卡片 | `w = 500`（居中） | 日历 4×160 + 3×16 = 688 宽也居中 ⇒ 最左格「+100 已到手」被左边缘切 37px、最右格「+160」被右边缘切 28px | `w = screen.width - 96`（与主页主卡同一条内容边距） |

> ⚠️ 这一条差点走偏：第一反应是"把遮罩调黑"，因为背景字看起来"太亮所以抢注意力"。
> 但调黑只是让问题**看不见** —— 换个奖励数值（字更宽）照样会露出来，而且"背景字被切"这件事本身还在。
> **调参治不了碰撞，让几何建立依赖才行。** 两条修复现在各有一对 `check-preview` 断言盯着。
>
> 顺带一条**给"工具"本身的标准**：检测器的头号指标不是"能发现问题"，而是
> **"报出来的都是真的"**。一个总在误报的检测器比没有检测器更糟 —— 它会让真问题埋进噪音里。
> 所以每加一条判定，都要拿"已知的真 bug"当输入跑一遍（`_inject-overlap.js` 把四条真实缺陷
> 重新造出来，确认探针**真会红**）；报红之后还要逐条目视确认，宁可漏报也不误报。

**然后玩家贴了一张截图过来："你看这不是字重叠了。"** 而当时探针写的正是"合计 0 处重叠"。
—— 这一轮最值钱的东西不是那条修复，是**探针为什么会漏**。

漏的是**阈值造的假绿**。判定要求"交集占到较小那个的 25% 宽 / 35% 高"才算重叠；
这条阈值本身没错（它是为了压掉"相邻两行"这种正常排版），
但它顺手挖出一个**盲区**：两段文字只压进去 3~4px 时，既不算"重叠"、也不算"过挤"
（过挤那条只查**没**相交的），于是从报告里静默消失。

真正的根因在主页三张统计卡里（`ui.stat`）：

| 位置 | 原来是 | 根因 | 现在 |
|---|---|---|---|
| 统计卡三层 | `valueCy = o.y + o.h * 0.60`、`labelCy = o.y + o.h - 16` | "数值"的下沿**不是数值基线**：单位要下沉 `vs×0.28` 再算半高，整块往下探了 ≈19.5px ⇒ 单位与标签的墨迹**恰好相切**。h=100 时上下净空各只剩 4px | 三层**自上而下流式排布**：先量高度、按 6px 最小净空排下来、再整体居中；`h` 100 → 108 |

于是探针做了两件事，缺一不可：

- **把尺子从"盒子"换成"墨迹盒"。** 盒子是按字号给的正方形，而笔画没那么高：
  20px 的西文数字墨迹只有约 14px，盒子上下各多留 3px；120px 的大数字则多留 17px。
  所以"盒相交 4px"在小字上是"糊在一起"、在大字上什么都不是 —— 拿盒子当尺子，
  阈值只能二选一：**小字漏报，或大字误报**（两件事都发生过）。
- **单列一类「贴死」并计入总计。** 墨迹相交不足 35%、或只相隔 2.5px 以内的组合，
  单列出来且**算进最后那句"N 处文字相撞"** —— 否则报告末尾那句话又会变成假话，
  而它恰恰是把玩家反馈挡在门外的那句话。

改完之后，`_inject-overlap.js` 新增的第 ⑤ 条注入（把魔数排布 + h=100 一起改回去）
会被准确抓出来，报的正是那三个组合：

```
[home / 主页] 可见文字 32 个 · 重叠 0 处 · 贴死 3 处
  ▩ 「/24」  ▩ 「皮肤」      —— 笔画贴死(墨迹相交 21.6×0.0)
  ▩ 「/19」  ▩ 「成就」      —— 笔画贴死(墨迹相交 21.7×0.0)
  ▩ 「天」   ▩ 「累计签到」  —— 笔画贴死(墨迹相交 20.0×1.4)
```

> **规则没有"报红了"的证明，就等于没有规则。** 注入验证现在共 5 条，
> 19 项全通过，四个文件逐字节还原。
>
> 还有一条教训顺带记下：**"看起来是问题"和"量出来是问题"经常不是一回事。**
> 这一轮我先猜是"遮罩太淡"，改完截图对比才发现背景只暗了一点、切字一点没变 ——
> 撤掉改动，去找真正的几何依赖。之前的"统计卡太挤"也一样：
> 第一反应是"调小字号"，量完才发现是 `h` 少给 8px。

**另外，锚点表抄了两遍就会不同步。** `smoke-render.js` 里有一份主页布局表的镜像
（用来算"该点哪里"），它长期停留在"还有 `hint` 那一行"时代的旧值。
漂移的表现**不是报红，是点击悄悄落偏** —— 卡片本来就够大，偏 10~23px 依然点得中，
断言照样是绿的。现在 `check-preview` 多了一条断言专门盯这份镜像。

---

**然后是第四次、两张截图一起过来。** 两个缺陷——探针在两端都写着"0 处文字相撞"：

| # | 位置 | 症状 | 探针为什么没报 |
|---|---|---|---|
| ① | 签到页 · 「累计里程碑」标题 | 30px 的标题墨迹**扎进日历最后一排格子 7px** | 「压边」要求"块画在文字**之后**"；日历格子画在标题**之前**。而且格子不是文字，文字↔文字那条也求不出交 |
| ② | 金潮 · READY 面板规则行 | 「★ 金块会横向游走…」35 字符 @25px ≈ 870px，卡片只有 632px，真机左右各溢出 52px+ | READY 面板**按模式渲染**，而探针只测了默认（经典）那一个 ⇒ 覆盖面不够，又是一个"看起来非常可信的 0" |

两个都修好了，但这一轮的产出仍然是**判定类别**（不是那两行代码）：

- **「越界」`outbound`** —— 文字捅出**它所属容器**的左右边界。容器 = 文字中心落在其内、
  画在文字**之前**、面积 ≥ 1.2 倍字、宽度 ≥ 半屏（排除装饰小图形与路过的红块/金块）、
  由**路径填充**画出的矩形里**面积最小**的那个。超出 > 3px 才报。
- **「压块」`block`** —— 文字跨在一个**实心块**的边界上（中心**不在**块内）。四条约束把噪音压到零：
  块画在文字**之前**、**同一屏幕层**、横向重叠 ≥ 40% 字宽、纵向 ≥ 4px 且 ≥ 25% 墨迹高，
  且中间没有 ≥ 0.8 不透明填充遮挡。

> **「同一屏幕层」是防假阳性的关键。** 每次全屏级 `fillRect`（w≥600 且 h≥700）让 `layer++`。
> 有了它才能把"浮层遮挡背景"（跨层，正常）与"同区块内图形切字"（同层，真问题）分开 ——
> 否则签到浮层卡片的背景会被每一条它盖住的字刷一遍。

两个几何量之间**必须真的建立依赖**，这一轮的两处修复都是这件事：

| 位置 | 原来是 | 根因 | 现在 |
|---|---|---|---|
| 签到页区块间距 | `CAL_DY = 400`、`MILE_DY = 762`（两个都写死） | 日历实际高 316，从 400 排到底 = 716，而里程碑从 762 起 ⇒ 净空只剩约 4px，再加字号变化就扎进去了 | `MILE_DY = CAL_DY + CAL_H + SECTION_DROP + 11 + SECTION_GAP`（从**日历实际下沿**推出）；规则卡 `ruleCardY()` 用"顶部流 vs 底部锚定取 `max`"保矮屏不撞 |
| READY 规则行 | `const segs = [modeRuleText[i]]`（整行当一段画） | 文案派生自参数、长度不可控；既不能缩字号（读不动）也不能截断（切掉关键信息） | 新增 `ui.wrapText()` **按宽度折行**（中文按字断、逗号/破折号/空格之后优先断）；卡片高度由**实测行数**决定，标签药丸宽度改用 `ui.measure()` 而不是 `length*22` |

> 这一轮探针自己也在**几何上**踩过一次坑：`intersect(a, b)` 原来只返回 `{w, h}`，
> 于是 `coveredBetween()` 里拿 `q.l / q.r` 全算出 `NaN`，"中间有没有遮挡"永远判不出 ——
> **不报错、不抛异常，只是这条约束静默失效**。修成返回完整矩形 `{l,t,r,b,w,h}` 之后才生效。
> 又一次印证同一句话：**"没报出来"和"真的没问题"是两件事。**

`_inject-overlap.js` 现在把 **7 个真实缺陷**造回来（新增第 ⑥ 条：`CAL_DY` 与 `MILE_DY` 两处一起改回
旧值才复现；第 ⑦ 条：规则行改回不折行），**23 项全通过**，五个文件逐字节还原。
真机探针也从"12 个场景×状态"扩到 **15 个**（四个模式**各一个** READY 面板）。

## 六、成长系统(造型商店 / 成就 / 金币)

### 6.1 为什么加这一层

微信官方的小游戏设计指南把目标体系分成四层:**单局 → 每日 → 每周 → 长期**。
前两层原本已经有了(单局纪录、签到),**第四层是空的** —— 玩 100 局和玩 1 局,
玩家手里的东西一模一样。这就是"单调"的机制来源,不是玩法数值不够刺激。

### 6.2 核心约束:没有任何美术资源

所以造型不用图片,而是把外观**参数化**成 6 个变量:

| 参数 | 取值 | 效果 |
|---|---|---|
| `shape` | **16 种**轮廓(见下) | 轮廓形状 —— **在深色背景上,形状比颜色更可靠** |
| `body` / `accent` | 十六进制色 | 主体色 + 高光色 |
| `trail` | `none` / `ghost` / `ember` / `star` / `ribbon` | 移动时留下的痕迹,**四种形态四种画法** |
| `glow` | 布尔 | 外发光(史诗及以上) |
| `spin` | 度/秒 | 自转(**纯观感,不改变碰撞框**) |
| `halo` | 布尔 | 外圈光环 —— ⚠️ 已由 `TIER_MARKS` 按稀有度接管,`style` 里写不写都不影响 |

**16 种轮廓**:
`round` 圆角方 · `circle` 圆 · `diamond` 菱形 · `hex` 六边形 · `pentagon` 五边形 ·
`octagon` 八边形 · `triangle` 三角 · `star5` 五角星 · `star4` 四角星 · `cross` 十字 ·
`shield` 盾牌 · `drop` 水滴 · `gear` 齿轮 · `ring` 圆环 · `blob` 波形圆 · `heart` 心形

改一个色值就是一个新造型,零下载体积、零美术成本。

#### 6.2.1 稀有度 = **看得见的结构差别**,而不是换个色

起因是一个真实反馈:**"这些皮肤没有什么让我购买的吸引力。"**
翻代码后数出来一个很硬的事实 —— 24 款里有 13 款没有任何发光,而拖尾只有 4 种形态,
于是"普通 6 款 + 稀有 7 款"这 13 款**只靠「形状 + 两个色值」区分**。
**花了两档的钱,拿到的是同一层次的视觉。**

所以加了 `TIER_MARKS`:每往上一档,就多一件**不可能看错**的东西。

| 稀有度 | 视觉标记 | 实现 |
|---|---|---|
| 初始 / 普通 | 无 | 基准与入场档,不靠光效证明自己 |
| 稀有 | **断续描边** | `ctx.setLineDash` 在放大的轮廓上描一圈短划线 |
| 史诗 | **呼吸光环** | 外圈实线,亮度按 `sin(now/620)` 脉动 —— "会呼吸"比一圈死线更像"这东西是活的" |
| 传说 | 呼吸光环 + **环绕星点** | 3 个星点挂在与光环同一半径上公转,角度直接由时间算(不存相位,也就改不坏) |

> ⚠️ 两个分层纪律:
> ① **`framework/ui.js` 不认识"稀有度"这个概念** —— 它只知道 `edge / halo / orbit` 三个普通参数。
>    由 `gameplay/skins.js` 的 `visualOf(skin)` 把稀有度翻译过去。
>    和"存档层不认识模式语义"是同一条纪律。
> ② **`visualOf()` 是唯一的"造型 → 渲染参数"入口** —— 主页头像、商城卡片、游戏内本体、
>    拖尾残影四处都读它,不再各自读 `skin.style.*`。否则一改造型语义就要改四处,必然漏一处。

`markTextOf(skin)` 会把"这一档多出来的东西"说成中文(`呼吸光环 + 3 个环绕星点`),
**从 `TIER_MARKS` 派生**而不是手写 —— 与"规则速览由实际参数生成"是同一条纪律:
手写文案迟早和参数打起来("界面写着有光环、其实没开")。

**一条硬约束(自检会守)**:24 款造型的**完整视觉签名**(形状 + 拖尾 + 档位光效)**两两不同**。
这条约束查出来的第一个受害者就是新手的第一次消费 —— 见下一节。

### 6.3 24 款造型,**全部靠金币购买**

> ⚠️ 这里和早期版本有一个重要区别:曾经有 9 款是"达成战绩条件自动解锁"的。
> 已全部改掉 —— **没有"系统发给你"的造型,每一款都标价、都由玩家自己挑。**
>
> 这样做换来三件事:
> ① 玩家要的是"我想变成什么样",不是"系统给我什么";
> ② 只有一种货币、一条路径,规则一句话说得清;
> ③ **技术好的玩家并没有吃亏** —— 成就(§6.4)会发金币,打得越好赚得越快。
> 技巧驱动的方向保留了,只是兑现方式从"直接发造型"改成"买得更快"。

按稀有度分五档,价格严格递增(**商城按这个顺序铺货,不打乱排序**):

| 稀有度 | 数量 | 价格区间 | 代表 |
|---|---|---|---|
| 初始 | 1 | 免费 | 初心 |
| 普通 | 6 | 180 ~ 560 | 苔痕 · 沙丘 · 潮汐 · 枫叶 · 薄荷 · 莓果 |
| 稀有 | 7 | 660 ~ 1500 | 熔岩 · 疾风 · 湛蓝 · 幽紫 · 落霞 · 星尘 · 棱镜 |
| 史诗 | 5 | 1680 ~ 2450 | 苍玉 · 零度 · 六芒 · 蜂蜜 · 珊瑚 |
| 传说 | 5 | 2700 ~ 3800 | 极光 · 陨铁 · 幻梦 · 无常 · 黑洞 |

**集齐全部 = 35860 金币。** 校准点:一局约 25 秒 ≈ 20 金币 →
**第 9~10 局就能买下第一款(180 金币)** —— 这是整个长期目标的"入场券",不能比这更晚。

> ★ **第一款必须和默认造型"一眼看得出不一样"。**
> 上面那条签名约束抓出来的第一处就是它:苔痕(180,新手第一款买得起的)原来是
> `round` + 无拖尾 + 无光效,而免费的初心**也是** `round` + 无拖尾 + 无光效 ——
> 两者完整签名完全相同,只差两个绿。也就是说新手花掉第一笔 180 金币,
> **买回来一个跟自己已经有的东西长得一模一样的东西。**
> "没有购买吸引力"这件事,最锋利的一刀恰恰砍在最该成交的那一次上。
> 现在苔痕是 `blob`(不规则有机形)+ `ghost`(淡残影)——"一直在长"的东西不该是个规规矩矩的圆。

### 6.4 19 个成就,而且**每条都发金币**

分六组:入门 / 生存 / 技巧 / 里程碑 / 积累 / **收集**。

其中**「技巧」组是这一作独有的** —— 擦身 10 次、命不该绝(用满回命)、完美主义(无伤存活),
这些比"分数高"更能说明玩家真的玩懂了这个游戏。

**「收集」组(3 条)是后加的**,原因很直接:原来 16 条**全是玩法指标**
(存活 / 躲避 / 擦身 / 拾取 / 局数),**没有一条和收集有关** ——
于是"我买到第 10 款"这件事在系统里不发生任何事。
三个台阶刻意卡在收藏进度条的三段上(**入场 / 过半 / 全满**):
`集齐 5 款` +200 · `半个衣柜(12 款)` +600 · `全都要(24 款)` +1500。

> 它同时是**双向**的:造型要花金币买 → 收集到一定款数 → 又发一笔金币。
> 所以它也是给"想买但钱不够"的人的一句"再买两款就回本了"。
>
> ⚠️ 一个必须守的会计细节:`career.skinsOwned` 是 career 里**唯一不由"一局"产出**的字段
> (它是商店里发生的事)。所以它在**三个时刻**被显式写入 —— 进商城页时对齐一次、
> 买完当场写一次、每局结算时(排在 `repairOwned()` **之后**)写一次。
> 少任何一处,玩家都会觉得"我明明买了它却不认"。
>
> ⚠️ 另一个:`Achievements.evaluate(career, unlocked, onlyFields)` 的第三个参数。
> 它默认"把所有待发的成就一次性结清"(那是**局末**该做的事);
> 商店必须传 `COLLECTION_FIELDS` 只结清收集组 —— 否则买一款造型会顺手把玩法成就也发掉,
> 而商店的飘字只报得出 `list[0]` 的名字:**说的和给的对不上**。

每条成就都带一笔金币奖励(60 ~ 1500,合计 **5050**),达成时立刻到账。
这笔钱定在造型总价的约 1/7:足以让"打得好"变成看得见的优势,又不至于跳过攒钱的过程。

> 设计上刻意做的一件事:**每条成就都能从 `career` 的某一个字段直接算出进度**。
> 于是判定和进度条是同一行数据推出来的,加一条成就 = 加一行数据。
> 代价是表达力受限,但换来了"改一个数字就能加成就"的极低维护成本。

### 6.5 经济闭环

```
局内表现 ─┬─→ 金币 ─────────────────────────┐
          └─→ 生涯统计 ─→ 成就 ─→ 金币 ─────┤─→ 购买造型(24 款,自己挑)
             每日签到(7 天周期)─────────────┤
             累计签到里程碑(3/7/14/30)───────┤
             分享(每日 ≤3 次)───────────────┘
```

四条收入来源:局内表现(主力,一局 15~40)、成就奖励(合计 5050)、签到(周期内单日 100~320,
一轮合计 1320;累计里程碑额外 100/200/400/800)、分享(每天最多约 390,与签到合计封顶)。

> 收集成就(§6.4)让这条闭环多出一个**小回路**:金币 → 造型 → 金币。
> 它是"买了就响"在数值上的那一半。

**金币是只进不出的软货币**(个人主体不支持内购,这里没有付费入口),所以数值给得宽松 ——
它的作用是"让积累看得见",不是卡玩家。但也不能太松:造型两天就买完了,目标感立刻消失。

> 这一轮之前的商店恰好把商品演示成了最差的样子 ——

> **越贵的,在商店里越看不出它贵**)、**拖尾从来没画过**(可它是游戏里最显眼的差异)、

> 玩家在商店里花的钱,要在这里被再确认一次"它算数";否则买造型这件事只在商店里存在。

> ⚠️ 详情弹层里的**实时预览不等于"在游戏里试穿一局"**。真正的试穿要临时改装备、
> 再把 Game 场景推上导航栈(而 Game 是 `replace` 进入的,没有"从哪来回哪去"的栈语义),
> 会给"存档里留下一个没买却穿在身上的造型"开口子。所以先用大尺寸实时预览 ——
> 它解决的是"看不清"这个真正的原因。

> 金币的两笔收入在结算面板上**分开显示**。合成一个数字会丢掉
> "打得好 = 赚得快"这条信息,而它正是技巧驱动唯一的兑现方式。

> 并**用正则解析服务端的 `MODE_LIMITS` 表逐值比对**，还会反向检查云端没有多余模式。

> ⚠️ **主页布局改了就同步改预览页。** 布局表是 `home-scene.js` 顶部的 `L`
> （`bottom() + dy` 的底部锚定形式），预览页对应 `HOME_LAYOUT`。
> 换了绝对坐标的话，`smoke-render.js` 里的点击会全部落空，而断言**依然可能是绿的**
> —— 这一轮就踩到过：`HOME.signinCard` 还写着旧的 `safeTop + 556`，点击变成空点。

> ⚠️ **改动成长系统后,务必跑一次自检**(见下一节),它会检查三件最容易出事的:
> ① `achievement.field` 是否真的存在于 `career` —— **字段名打错一个字母,这条成就永远达不成,而且不报任何错**;
> ② 造型用到的 `shape` 是否在渲染层真的实现了 —— 否则会**静默回落成圆角矩形**,两款造型长得一模一样;
> ③ 造型表是否还保持价格升序、稀有度与价格是否还单调对应;
> ④ **24 款造型的完整视觉签名(形状+拖尾+档位光效)是否还两两不同** ——
>   全撞的三款在 96px 的卡片上就是同一个东西,而这正是"没有购买吸引力"最锋利的那一刀。

> 重叠是**几何问题**，读源码看不出来 —— 一个坐标摆在 `safeTop + 372`、另一个摆在 `+376`，
> 差 4 像素在代码里毫无异常，在屏幕上就是两行字压在一起。
> 所以 `_overlap.js` 把每次 `fillText` 的坐标 / 字号 / 对齐 / 透明度 / **调用行号**全记下来，
> 算出真实矩形再两两求交，报出"哪两段字、在哪个坐标、是哪一行代码画的"。
>
> 但比"能发现问题"更重要的是**"报出来的都是真的"** —— 这套工具的排除规则全是假阳性逼出来的：
> ① `save/restore` 必须真的实现（打成 noop → `ui.sprite({glow:true})` 的 alpha 泄漏到整页，
> 报出"0 个文字块"的假结论）；② 必须模拟 `clip()`（商城把滚动内容裁在 1414，
> 第 4 行卡片名称画在 1465 —— 坐标上压在返回按钮上，玩家永远看不见）；
> ③ 必须按**累积不透明度**判断遮挡（单层 74% 遮罩下的 92px 白字仍然明显可见，
> 而 76% 遮罩 + 不透明弹层卡片才是真的盖住）；④ 只取**最后一帧**（渲染 60 帧会让同一处重叠报上千次）。
>
> ⑤ 更根本的一条：**几何判定要用"墨迹盒"而不是"盒子"**。
> 盒子是按字号给的正方形，笔画没那么高 —— 20px 的西文数字墨迹约 14px（盒子多留 3px），
> 120px 的大数字多留 17px。所以"盒相交 4px"在小字上是"糊在一起"、在大字上什么都不是；
> 拿盒子当尺子，阈值只能二选一：小字漏报，或大字误报 —— **两件事都发生过**。
>
> 它还有两条**独立判定**：「压边」= 文字跨在实心圆角块（含**描边**）的边界上，
> 也就是"图形切字"（详见 §5.8）—— 这是"文字 ↔ 文字"永远看不见的一整类问题，
> 却最贴近玩家说的"字重合看不清"。判定要同时满足：块画在文字**之后**、
> 压掉的是一条**实质的带**（≥ 半个字高）、且只取包含比最大的那个块 —— 少了任何一条都会刷屏。
> 「贴死」= 墨迹相交不足 35%、或只相隔 2.5px 以内 —— 这一类**计入总计**，
> 因为"合计 0 处"曾经正是一句被阈值造出来的假绿。
>
> 一句话：**诊断工具的头号指标不是"能发现问题"，而是"报出来的都是真的"。**
> 每加一条判定，都用 `_inject-overlap.js` 把"已知的真 bug"重新造出来确认它**真会红**；
> 报红之后还要逐条目视确认（探针报的每一条都开图看过），宁可漏报也不误报。

> `check-scaffold` 里第 7 条「注释吞代码」是被一个真实的坑换来的：
> 一个块注释少写 `*/`，会**静默吞掉几十行之后的代码**（那下面另一个注释的 `*/` 把它收掉了）。
> `node --check` 看不出来（未闭合注释不是语法错误），require 路径检查也看不出来
> （它扫的是剥掉注释后的源码，被吞掉的 require 根本不在里面），
> 直到运行时才炸出一句 `Storage is not defined`，而行号还是准的。

> 已去掉早先的 `hint` 项 —— 非入榜提示移到了分数正下方，不再是一个独立锚点）、
> **设计规范层 + 排版语言层**（13 个新色板键逐值 + `SPACE / RADIUS / TYPE` 三张 token 表逐值 +
> **17 个原语存在性**：`bg / card / pill / divider / sheen` + `section / stat / kv / badge / empty /
> spinner / icon / monogram / measure / fitText / ellipsis / hashCode` + 渐变缓存的写法 +
> **`ICONS` 14 个图标名两端同名同序** + **五个画面切换按钮与三处分发分支**）、
> **五个机制开关的默认值**（`OBSTACLE_SWAY` / `COMBO_*` / `PICKUP_DRIFT` / `LANE_*` 与 `config.GAME` 逐值比对）、
> 以及内联模块的函数个数(`checkin` 8 个、`modes` 10 个、`effects` 9 个、三画面共 11 个)。
> 它还会检查**存档写入口径是 `v4`**（`v3` / `v2` 只作为读取迁移的来源，不再写入）。
>
> ⚠️ 商城布局那一段是**从真机源码读出数值再比**的，不是把数字写死在这里 ——
> 写死的话，真机改了常量（本轮 `CELL_H` 226 → 274 就是这样）、这里忘了同步，
> 检查会一边宣称"一致"一边放行。
> 同理，`shapePath` 的切片标记也从"注释文案"换成了结构标记（`function sprite(c, opt) {`）——
> 本轮改了那句注释，切片就失效了。
>
> ⚠️ 它比对 token 表前会先**剥掉行内注释**：真机的 `TYPE` 表每行后面都挂了中文注释，
> 不剥掉的话"逐值一致"永远比不过（本轮真实踩到）。
> 侧栏的造型缩略图也是用真 canvas 跑同一个 `sprite()` 画的,所以形状不会出现"预览和真机不一样"。
> 它最后还会**把两端各 16 种轮廓与 14 个图标真的画一遍**（`stroke` / `fill` 也进指纹），
> 取路径操作序列当指纹，断言两两不同**且两端逐点一致**
> —— 字符串检查只能证明"分支写了"，证明不了"分支画出来不一样"。

> ⚠️ 预览页有一类 bug 是**任何静态检查都抓不到的**:它把真机模块**手抄**成内联副本,
> 抄漏一个字段、少内联一个原语,`node --check` 照样通过,而页面一打开就白屏。
> 本轮就踩到两个:预览页的 `button()` 没暴露 `opt`(真机 `ui.button` 是有的,
> 主页读 `b.opt.x` 直接崩),以及 `progress` 原语没内联(商城页崩)。
> 所以 `check-preview.js` 里加了两条**形状断言**(`button().opt` 必须存在、`progress` 必须内联),
> `smoke-preview.js` 则直接**把预览页跑起来并模拟点击** —— 只有真正执行才能证明它不是白屏。

### 换成别的玩法

分层设计保证只需替换两个文件:玩法规则写进 `js/gameplay/`,画面与交互写在 `js/scenes/game-scene.js`。
`js/framework/`、`js/platform/`、`cloudfunctions/` 全部无需改动 —— 闭环(结算、上榜、分享、埋点)会自动跟着走。
成长系统也无需改动:它只读 `career`,不关心战绩是怎么产生的。

## 八、分包(主包 4MB 是小游戏的生命线)

`game.json` 已声明一个分包:

```json
"subpackages": [
  { "name": "play", "root": "subpackages/play/" }
]
```

使用方式(必须先 await 加载,再 require **分包入口 `game.js`**):

```js
const Resources = require('./js/framework/resource-loader.js');
await Resources.loadSubpackage('play');
const levelData = require('./subpackages/play/game.js');
```

> ⚠️ 分包 `root` 目录根下**必须有 `game.js`**——它是分包入口(微信硬约定)。缺了它会直接编译失败:
> `Error: game.json: 未找到 ["subpackages"][0]["root"] 对应的 .../game.js 文件`。
> `check-scaffold.js` 已加这条校验,防止再犯。

**体积分配建议:** 主包 ≤ 2MB(硬上限 4MB)、分包不限单个大小、主包 + 全部分包总量 ≤ 30MB。
大图与音频优先放 CDN(用 `wx.downloadFile` 下载到本地缓存),完全不受包体限制。

## 十、常见问题

**Q:云函数调用很慢(第一次尤其慢)?**
A:这是云函数冷启动。给 `login` 和 `submitScore` 配置**预留并发实例**(云开发控制台 → 云函数 → 配置),并保持客户端 3s 超时 + 本地降级设计(骨架已实现)。

**Q:改完代码后排行榜没有更新?**
A:`getRank` 有 60 秒缓存(在 `configs` 集合里)。开发阶段可把 `getRank/index.js` 的 `CACHE_TTL` 改成 `0`。

**Q:好友榜一直空白?**
A:三步都要对:① `wx.setUserCloudStorage` 已上报分数(打一局后触发);② `rank-scene.js` 已 `postMessage` 通知子域;③ 子域用的开放数据域目录已在 `game.json` 的 `openDataContext` 中声明。另外好友榜只显示**同样玩过本游戏**的好友,自己一个人玩时是空的,属正常现象。

**Q:`require` 分包代码报"模块不存在"?**
A:分包代码在 `loadSubpackage` 成功之前不能 `require`,必须先 `await` 加载再引用。

**Q:包体超了怎么办?**
A:按优先级:① 大图/音频挪到 CDN;② 后续关卡和活动页放分包;③ 压缩图片(2 倍图足够,不要 3 倍图);④ 音频用 ogg/silk 压缩。
