# 作品版收口计划 · 寒假定档

> 生成日期：2026-09-29　适用：个人独立开发 / 1 人 / 微信云开发
> **定位变更：目标从「靠它赚钱」改为「上线一个能讲的作品」。**
> 时间锚点：**2027 年寒假（1 月）** —— 不设更早的 deadline，也不无限期拖下去。

---

## 〇、决策依据（为什么是这条路）

- 广告收入的规模由 **DAU** 决定，DAU 由 **推广** 决定，而推广是**持续投入的运营活儿**，与长期的时间投入正面撞车。
- 多数个人开发者第一作**不赚钱**，能赚钱通常在第二、三作 —— 那是 1–2 年的尺度。
- 你已经拥有最费时的部分（分层骨架 + 跑酷玩法已写通），把它"做完上线"的**边际成本极低**。
- 结论：**现在不为钱做，为"我独立做上线过一款游戏"这个事实做。**

### 唯一的一把尺子

做任何决定前问两句，**两个都否 → 砍**：
1. **它能让我上线吗？**
2. **它能让我在技术评审里讲出来吗？**

---

## 一、范围冻结（这就是你的护城河）

范围冻结的意义：**防止被"再加个功能"拖住。** 冻结之后，只准减，不准加。

### ✅ 保留（上线必需 + 能讲）

| 模块 | 为什么保留 |
|---|---|
| 跑酷核心玩法 + 真机手感调优 | 作品本体，唯一值得反复打磨的东西 |
| 首页 / 游戏页 / 结算页 / 商城页 / 签到页 / 排行榜页 | 完整闭环 |
| 本地最高分 + 云存档（简化版） | 演示后端能力 |
| **自建全服排行榜** | 技术亮点，且**不需要关系链授权**，冷启动可用 |
| 分享（基础能力，非强制） | 上线后自然传播的唯一抓手 |
| 隐私合规弹窗 + 适龄提示 | **上线硬性要求，必须有** |
| 基础埋点 | 让你能拿出"真实使用数据"讲故事 |
| **造型系统（24 款，全部金币购买，含稀有度视觉签名）+ 成就（19 项，达成发金币）** | 2026-10-01 加回，10-02 七次修订定稿，理由见下方修订说明。**零美术成本、零运营成本**，且是作品说明与软著里最好讲的一块。七次修订解决了"玩家在掏钱之前从没见过他要买的东西"这个致命问题 |
| **独立签到页（7 天周期 + 累计里程碑，给金币）** | 同上，仍是"一次做完就完事"的系统。7 天周期让"明天再来"有明确反馈，累计里程碑挂在周期之上做长期钩子 |
| **金币经济** | 给签到与成就一个出口（原来签到给的金币**没有出口**，是个断掉的循环）。七次修订的收集成就又给它加了一个**小回路**：金币 → 造型 → 金币 |
| **四种玩法模式（经典 / 疾风 / 金潮 / 死线）** | 2026-10-01 四次修订加入，10-02 五次 / 六次修订定稿。**纯数据，不是新系统**：共用同一套规则代码，每个模式各启用一条彼此正交的独有机制（障碍摆动 / 金块游走 / 走廊摇摆），经典一条都不开。加第五个模式的成本接近于零 |
| **粒子特效层（固定容量池 + 无状态环境粒子）** | 同上。纯渲染层，只读不写 `world`。它是"这一作看起来不像作业"最便宜的一步，也是能在技术评审里讲清"为什么不用 shadowBlur"的地方 |
| **界面设计规范层（token 表 + 绘制原语）** | 2026-10-02 五次修订加入。把圆角/间距/字号/缓动抽成常量表，并沉淀 `bg/card/pill/divider/sheen` 五个原语，让**五个**页面用同一套规则说话。**没有新增任何系统或资源**，纯粹是把已有的界面写法收拢、消灭散落的一次性数值 |
| **排版与图形语言层（区块标题 / 指标 / 空状态 / 矢量图标 / 字母头像）** | 2026-10-03 八次修订加入。解决"好多都是单一的文字显示"—— 先前所有文字都只是"摆在坐标上的 `fillText`"，**靠字号表意而不靠层级**。这一层补上文字周边缺失的结构：`section` 区块标题（五页同一套语气）、`stat` 指标（图标/数值/单位/标签）、`empty` 空状态、`spinner` 加载指示、14 枚矢量图标、哈希定色的字母头像。同样**零美术资源、零云函数、零集合、零新页面** —— 表现形式是"改几个色值/调一个函数"，正是"一次性做完、之后不需要你管"的那一类 |

### 🔄 修订说明（2026-10-01）：为什么把"皮肤/成就/签到"加回来了

**这看似违反了"只准减，不准加"，实际没有。** 原判断有一个前提是错的：

> 原判断："多主题/皮肤增加的是**美术成本**，不是技术亮点" —— 这个前提假设皮肤=美术资源。

**而本作没有任何美术资源。** 造型是把外观**参数化**成 6 个变量
（16 种轮廓形状 / 主体配色 / 高光配色 / 4 种拖尾形态 / 外发光 / 自转 + 光环），
全部用 Canvas 画出来。**加一个造型 = 改几个色值**，成本接近于零。

同样，"每日签到 / 成就"被归为"运营玩法"也不准确。**运营玩法**指的是需要你天天上线维护的东西
（每日任务链、周常、限时活动、赛季）—— 那些**仍然全部砍掉**。
而**签到和成就是"一次做完、玩家自己消费"的系统**，写完就完了，不需要你管。

所以真正的边界不是"玩法 vs 运营"，而是：

| | 处理 |
|---|---|
| **一次性做完、之后不需要你管**（造型、成就、签到、金币经济） | ✅ 做 |
| **需要持续投入运营**（任务链、活动、赛季、社交、买量） | ❌ 砍 |

而且这一层解决的是一个**真实的产品缺陷**：原来玩 100 局和玩 1 局，玩家手里的东西一模一样 ——
这正是"感觉很单调"的机制来源。补上它之后，这一作才有了"跨局"这个维度。

### 🔄 二次修订（2026-10-01 晚）：造型从"条件解锁"改为"全部金币购买"

改之前是 9 款"达成战绩条件自动解锁" + 3 款金币购买。**改成 24 款全部金币购买。**

- **理由**：玩家要的是"我选我要变成什么样"，不是"系统发给我什么"。而且只有一种货币、一条路径，
  规则一句话说得清，不用解释两套逻辑。
- **技巧驱动没有丢**：改成让**成就发金币**（当时 16 项合计 2750；第七次修订加入收集组后为 **19 项 / 5050**）。打得越好赚得越快，
  兑现方式从"直接发造型"变成"买得更快"。
- **同时把"丰富"做实**：12 款 → 24 款，4 种形状 → 16 种，拖尾从布尔 → 4 种形态，
  新增稀有度五档（与价格区间单调对应）。这些都有断言锁死（形状是否真的被渲染层实现、
  16 种是否全部被用到、价格是否严格递增），不是靠形容词。

> 副作用（正面的）：造型与成就系统是**软著"独创性"最实在的材料**，
> 也是技术评审里能讲出一整段设计权衡的东西（见 `README.md` 第五节的模型说明）。

### 🔄 三次修订（2026-10-01 深夜）：主页重做 + 「图鉴」升级为「商城」 + 独立签到页

用户反馈"想要一个主页面、商城能买皮肤、签到要有签到页面"。三件事一起落地，
**仍然全部落在"一次性做完、之后不需要你管"的一侧，没有违反范围冻结。**

| 改动 | 做了什么 | 为什么 |
|---|---|---|
| **主页重做** | 造型头像 + 昵称 + 金币 + 历史最高分 + 三张统计卡 + 目标行 + 签到卡（未签时金色呼吸描边 + 红点）+ 三个入口 | 原来的主页信息太薄，"我在变强"看不出来。统计卡把三套进度的数字直接摆在脸上 |
| **「图鉴」→「商城」** | 页面改名；新增**稀有度筛选条**（全部 / 普通 / 稀有 / 史诗 / 传说）；顶部加「已拥有 N/24」+ 收藏进度条 + 生涯摘要 | 24 格平铺成 8 行、"整页看不完"。筛选是货架型界面最基本的可用性要求 |
| **独立签到页** | 新建 `signin-scene.js` + 把规则抽成纯逻辑 `checkin.js`；**签到奖励从"连签加成封顶"改为"7 天周期"**，并新增累计里程碑 | 原来签到只是主页上的一个按钮，没有"明天再来"的仪式感；而"连签加成封顶 7 天"的问题在于：第 8 天和第 30 天给一样多的钱，毫无反馈 |

**关于签到规则从"封顶"改成"周期"的设计权衡**（这段在技术评审里可以直接讲）：

- 无限递增 → 长连签的收益会压过局内表现，主力收入来源被签到抢走，玩法失去意义。
- 简单封顶 → 数值上安全，但没有反馈：连签第 8 天发现跟第 7 天一样，回访动力归零。
- **7 天周期** → 循环回绕，既有"今天比昨天多"的即时反馈，又在数值上收敛（一轮合计 1320，
  不足以买下中高档皮肤，所以签到始终是"补贴"不是"主力"）。

两层钩子分工明确：**7 天周期**解决"明天再来"（断签重置周期 → 有回访压力），
**累计里程碑**（3/7/14/30 天）解决"这周/这个月再来"（不要求连续 → 断了也不至于彻底放弃）。
断签只重置**这一轮周期**，不清空**累计天数** —— 玩家真实攒出来的天数不应该被抹掉。

> 契约提醒：签到公式在客户端（`js/gameplay/checkin.js`）与云函数（`cloudfunctions/dailySign/index.js`）
> 各有一份，**必须完全同口径**（`BASE_REWARD 100 / STREAK_BONUS 20 / CYCLE_DAYS 7 / CYCLE_BONUS 200`）。
> 改一处必须两处一起改，否则服务端发的钱和客户端显示的对不上。

### 🔄 四次修订（2026-10-01 深夜）：四种玩法模式 + 粒子特效层

用户反馈"可以增加其他玩法模式和特效"。两件事都落地了，**但它们的性质完全不同**，
边界也因此不同 —— 这一轮最值得记下来的就是这条边界。

| 改动 | 边界 | 为什么 |
|---|---|---|
| **四种玩法模式** | 属于**规则/设计层**，允许迭代 | 模式是**纯数据**（`modes.js`），不加任何新系统：不新增数据库集合、不新增云函数、不新增页面。规则代码仍然只有一份 |
| **粒子特效层** | 属于**表现层**，允许迭代 | 它是一个纯渲染模块（`effects.js`），**只读不写 `world`** —— 一旦特效开始影响判定，"看起来躲开了"和"真的躲开了"就会分家 |

**范围冻结的原文是"砍系统，不砍设计"。** 这一轮验证了这条边界是可执行的：
四个模式 + 一套特效，对系统层的改动只有三处 ——
`storage.js` 的存档版本 +1（新增 `mode` 与 `bestByMode` 两个字段）、
`submitScore` 的校验上限从"一个常量"变成"一张按模式查的表"、
以及 `game-scene.js` 里多了一段调用。**没有新增一个集合、一个云函数、一个页面。**

四条设计上刻意的克制，理由写在这里免得日后自己想不起来：

1. **只引入一个真正的规则开关（`timeLimit`）。** 参数边界清晰（同样的规则跑不同的数值永远可控），
   而每加一个规则分支，组合数与测试成本都翻倍。四个模式里只有「死线」真的需要新规则。
2. **只有「经典」计入全服榜。** 跨模式比分数不公平（死线 60 秒封顶，永远赢不了无限时长的经典）。
   一张榜只有一把尺子才是可比的 —— 把不可比的分数放上去，榜就失去了唯一的意义。
3. **纪录按模式分开记（`bestByMode`）。** 四模式共用一个 `bestScore` 的话，其中三个模式永远刷不出
   "新纪录" —— 玩家做对了一切却得不到确认，正是"没有跨局反馈"的老毛病。
4. **收益与风险同步放大。** 金潮模式在金块变多的同时，提高了"贴着红块生成"的概率。
   否则这个模式只是"变简单了"，而不是"变得更贪了"。

特效的唯一取舍是**帧率**，所以有三条硬约束：固定容量粒子池（池满静默丢弃，不做扩容）、
禁用 `shadowBlur`（逐像素卷积，低端机极贵）、环境粒子做成无状态纯函数（不占池、零 GC）。
以及一条纪律：**破纪录的彩带必须画在结算遮罩之上**，否则最该被看见的那一次庆祝会被面板压住。

> 副作用（正面的）：这一轮又是软著"独创性"的好材料 ——
> "一个模式 = 一组参数覆盖 + 至多一个规则开关"这句话本身就是一段能讲清的设计权衡；
> 而上限推导（`rateOf()`）与"改参数忘了改上限"的断言，说明防作弊上限不是拍脑袋来的。

### 🔄 五次修订（2026-10-02）：UI 统一规范 + **推翻"只调数值"的多模式方案**

用户反馈两条："优化一下 UI 界面" + "我感觉这四个玩法太像了吧"。**第二条是这一轮最值钱的收获 ——
它证明四次修订里那个"只引入一个规则开关"的判断，在体验上是站不住的。**

**① "四个玩法太像"的根因：差异全落在数值上。**

四次修订时四个模式其实只是"同一套规则 + 四组不同数值"：都是左右拖动躲红块，只是更快、金块更多、
限时更短。**玩家从头到尾做的动作一模一样，只是快慢不同** —— 体感必然"像"。把数值差距拉到极端也治不了：
把速度调到两倍，玩家做的事还是那一件。**"调参"治不了"动作重复"。**

**解法：每个模式各给一条彼此正交的独有机制。** 三条机制改的是**三件不同的事**：

| 模式 | 独有机制 | 改的是哪一维 | 开关（默认一律"完全不生效"） |
|---|---|---|---|
| **疾风** | 障碍横向摆动 | **怎么躲** | `OBSTACLE_SWAY: 96` + `OBSTACLE_SWAY_WAVE: 0.009` |
| **金潮** | 拾取连击链 | **为什么贪** | `COMBO_ENABLED: true` + `COMBO_STEP: 0.6` + `COMBO_MAX: 3` |
| **死线** | 活动走廊收窄 | **空间有多大** | `LANE_SHRINK_SECONDS: 55` + `LANE_MIN_RATIO: 0.66` |
| **经典** | *（一个都不开）* | 基准 / 尺子 | —— |

> ★ **六次修订已在此表基础上补上"可见形态"**：金潮再加 `PICKUP_DRIFT: 150`（金块游走，标签→「追猎」）、
> 死线再加 `LANE_SWAY: 110` + `LANE_SWAY_PERIOD: 5`（走廊摇摆，标签→「限时 · 摇摆」）。
> 见下方"六次修订"一节 —— 那张表说明的是**当时**的状态，这里留作对照。

> **这里修正了四次修订的第 1 条克制**："只引入一个真正的规则开关"在当时是对的（省钱、省测试），
> 但它把"四个模式不一样"这件事**押在了数值上**，而数值差异是玩家体感最弱的差异。
> 现在改成"每个模式一个机制"，规则内核里多了三个开关（六次修订后又各补了一个"可见形态"开关）—— 但**默认值一律关闭**，
> 所以**经典模式的行为与加机制之前逐字节一致**（老测试一条都不用改，这就是"默认不生效"的价值）。

**② 三个设计判断（踩过才想明白的）：**

- **摆动由纵向位置 `y` 驱动，不由时间驱动。** 时间驱动的话速度越快能看到的波形越少，"预判"就退化成运气；
  用 `y` 驱动后无论多快玩家看到的都是**同一段完整波形** —— 可学、可预判。这是机制能不能成立的数学前提，
  测试里逐帧验 `x = baseX + sin(y·WAVE + phase)·amp`（4032 次采样）就是在守这条。
- **收窄停在 66%，而且收到底就停。** 走廊最窄 750×0.66 = 495，减最宽红块 280 还剩 215，
  刚好够玩家（宽 96）挤过去 —— 再窄就从"有难度"变成"无解"。**难度必须来自选择变少，而不是选择消失。**
  停在固定值才有终点感，否则最后几秒会变成持续的不安。
- **连击里被撞不扣分，只把倍率打回原点。** 失去的是"接下来每个金块多拿一倍"的预期，比扣已到手的分数
  更想补回来。而断链本身是**沉默的**，必须显式飘字说出来。

**③ UI 统一的本质不是"加特效"，是"消灭一次性数值"。**

四个页面的界面原本各写各的：圆角 12 或 16、间距 16 或 20、字号 23 或 26 —— **单看都还行，拼在一起就散**。
所以抽出一个**设计规范层**（`js/framework/ui.js`）：四组 token（`SPACE / RADIUS / TYPE / Ease`）
+ 五个绘制原语（`bg / card / pill / divider / sheen`），并把老配色**只增不改**地补了 13 个键
（背景渐变两端、三层表面、两级描边、四个语义色的亮档）。

> **精致感真正的来源是三件小事**：统一圆角 + 1px 半透明描边 + 顶部一道内高光。不是花哨特效。
> **整屏只允许一处发光**（结算卡片破纪录时）—— 处处发光 = 处处不发光。
> `shadowBlur` 沿用了特效层的禁令，一次都不用。

**④ 范围冻结有没有被突破？没有。**
三条模式机制是**规则/设计层**（纯数据 + 规则内核里多组默认关闭的开关），
UI 规范层是**表现层**（一个纯绘制模块）。**没有新增集合、云函数、页面或美术资源。**

> 副作用（正面的）：这一轮是软著与技术评审里**最好讲的一段** —— 它包含一个完整的"发现问题 → 推翻自己的
> 旧判断 → 换一个不同维度的解法"的过程。评审者问"你怎么保证四个模式不雷同"，
> 答案不是"我调了参数"，而是"**数值差异是玩家体感最弱的差异，所以我改了机制**"。

### 🔄 六次修订（2026-10-02）：**机制必须是"看得见的运动"，不能只是一个数字**

用户反馈一条："这个疾风改的很好，其余两个玩法按照这个方向再改。" —— 注意它夸的是**疾风**，
而疾风恰好是唯一一个**红块真的在动**的模式。这条反馈推翻的正是五次修订的收尾判断：
"每个模式一条正交机制"做到了**规则上正交**，但金潮与死线**在玩家眼里仍然同质**。

**① 根因：机制强 ≠ 机制被感知。**

| | 五次修订的机制 | 玩家实际做了什么 | 看得见吗 |
|---|---|---|---|
| **金潮** | 拾取连击链（倍率 ×3） | 还是"去撞金块"（只是更值钱） | ❌ 倍率是一个**看不见的倍数** |
| **死线** | 走廊线性收窄 34% | 还是"左右躲"（只是地方小了） | ❌ 55 秒才走完，几乎察觉不到 |

疾风之所以好，是因为它同时满足三点：**有物理现象**（红块真的在动）、**有规律可预判**
（由 `y` 驱动，波形可读可学）、**每一块都不同**（相位随机）。于是把这三条**逐条复制**给另外两个模式：
给机制补一层**物理上可见的运动**。

**② 解法：把"数字"换成"运动"。**

| 模式 | 六次修订补的机制 | 玩家做的事变了 | 一句话规则 |
|---|---|---|---|
| **金潮** | 金块**自己横向游走**（匀速直线 + 折返），速度 = 基础 150 × **当前倍率**（连满 ×3 → 450） | 从"去撞金块"变成"**算落点、提前站位**" → **追** | 只要你动就追得上；你不动，一个也拿不到 |
| **死线** | 走廊**一边收窄一边整体左右平移**，振幅随收窄进度增长，周期恒定 5 秒 | 从"左右躲"变成"**跟着整个空间的节拍走**" → **随** | 空间在变小，而且还在漂 |

**③ 为什么这样设计（三个判断）：**

- **倍率同时成为"奖励刻度"与"难度刻度"。** 速度 = `PICKUP_DRIFT × comboMul`，于是"越贪越难追"
  从一句宣传语变成一个能算出来的数。金潮的机制标签也从「连击」改成「**追猎**」。
- **金块游走用匀速直线，不用正弦。** 匀速是全作最好读的运动（一眼看出往哪跑、可算落点）；
  而疾风读波形、死线跟节拍、金潮算落点 —— **三种运动"要动脑的地方刻意不同"**，正交才落到动作上。
- **走廊摇摆的振幅写在几何安全区里**：`amp = min(LANE_SWAY, full×(1−minRatio)) × 收窄进度`。
  因为幅度 ≤ 收窄腾出的余量，走廊**永远不会被推出屏幕** —— 这条约束在公式里，不靠运行时兜底夹取。
  周期恒定 5 秒（太快读不过来、太慢分不清在摆）。机制标签从「限时 · 收窄」改成「**限时 · 摇摆**」。

**④ 范围冻结有没有被突破？仍然没有 —— 而且这次连服务端都一行没改。**

金块的**数量**没变（游走只让它更难拿）、走廊的**生成间隔**没变（摇摆只让空间移动），
所以服务端的每秒得分上限表 `32 / 47 / 49 / 48` 原封不动，`rateOf()` 推导公式也不用动。
两个机制是**规则内核里多两个"默认不生效"的开关**（`PICKUP_DRIFT: 0` / `LANE_SWAY: 0`）。
**没有新增任何集合、云函数、页面。**

**⑤ 这一轮最值得记的一句话：机制的可感知性 ≠ 机制的强度。**

> 一个数值上很强的机制（倍率 ×3）如果玩家看不见，体感上就等于不存在；
> 一个数值上很弱的机制（走廊挪 110 像素）只要动起来，玩家立刻就能懂。
> 这也是"疾风改得很好"那条反馈的真正落点 —— 好不在强度，在**它动起来了**。

顺带记一条工程判断：**给可见物一个专属颜色，它才可被自动验证。**
金块的游走残影原本用金块的自身色，结果与粒子特效（拾取爆发、彩带）撞色，
冒烟测试无法分辨"残影画了没有"；改用专属的亮金 `#ffd166` 后，断言立刻变得可靠。
（残影比本体亮一档在语义上也更对 —— 余晖本来就该更亮。）

### 🔄 七次修订（2026-10-02）：**演示即商品** —— 造型的"卖得出去"

用户反馈一条："**这些皮肤没有什么让我购买的吸引力呀。**"

这条反馈逼出了一个此前一直没问过的问题：**玩家在掏钱之前，"见过"他要买的东西吗？**
翻代码的数下来，答案是没有 —— 而且是被商店自己挡住的。

**① 四条根因（每条都能指到具体的代码行）：**

| # | 根因 | 证据 |
|---|---|---|
| 1 | **商店把商品演示成了最差的样子** | 卡片预览只有 68px；未拥有的被压到 35% 不透明度（`dim: !owned`）；**未拥有的直接关掉发光与光环**（`glow: style.glow && owned` / `halo: style.halo && owned`）—— 而发光正是史诗档、光环正是传说档**唯一"贵在哪"的标志**。`skin.desc` 那 24 条文案**全项目搜过，从未被渲染**。**结论：越贵的，在商店里越看不出它贵。** |
| 2 | **一半的造型只看得出换色** | `glow` 只在 epic/legend 开 → 24 款里 **13 款无任何发光**；拖尾只有 4 种形态。于是"普通 6 款 + 稀有 7 款"这 13 款**只靠「形状 + 两个色值」区分** |
| 3 | **买了没有任何回响** | 16 条成就**全是玩法指标**（存活/躲避/擦身/拾取/局数），**没有一条与收集有关**；结算面板会写"再攒 N 金币"但**从不显示"已收集 N/24"** |
| 4 | **自相矛盾** | `ui.sprite()` 用 `ctx.shadowBlur = 18` 做发光，而 README / 软著 / `effects.js` / `check-preview.js` 四处都写着"绝不使用 shadowBlur"—— 它偏偏挂在**玩家每帧**与**商店 24 张卡**上（最贵的地方） |

**② 解法：四处改动，一条判断。**

> ★ **演示即商品。舍不得把东西演示好，就别指望有人想要它。**

| 改动 | 做了什么 |
|---|---|
| **看得清** | 卡片预览 68 → 96px，**带上拖尾示意**（此前从未画过）；未拥有**不再压暗、不再关光效**；补上单行 `desc`。"未拥有"改由**卡片本身**表达（虚底 + 稀有度淡边 + 价格行），不靠把商品涂灰 |
| **能细看** | 新增 **640×866 详情弹层**：220px **实时预览**（自转/拖尾/呼吸光环/环绕星点全在动）、完整 desc、由数据派生的"这一档多了什么"、拖尾中文名、买/换/还差多少主按钮 + 进度条、点遮罩关闭 |
| **贵一档要看得见** | `TIER_MARKS`：稀有 = **断续描边** / 史诗 = **呼吸光环**（`sin` 脉动）/ 传说 = 呼吸光环 + **环绕星点**。**每往上一档就多一件"不可能看错"的东西** |
| **买了要响** | `career.skinsOwned` + **3 条收集成就**（集齐 5 / 12 / 24 款 → 200 / 600 / 1500 金币）+ 结算面板新增 **`造型 N / 24`**（全收集变金色） |
| （顺手） | `sprite()` 的 `shadowBlur` 换成 **4 层同心描边近似**，与全作禁令对齐；`check-preview` 的 shadowBlur 检查从"只查特效层"扩到 **`sprite()`** |

**③ 三个设计判断（这一轮真正想清楚的）：**

- ★ **"演示即商品"是一条纪律，不是一次美化。** 凡是"玩家要花代价得到的东西"，
  都必须在他付代价之前被完整呈现。这条纪律适用于商店，也适用于任何未来的增值内容。
- ★ **"贵一档"必须是结构差别，不是换色。** 只改色值的两档，在 96px 的卡片上就是同一个东西。
  结构差别（多一件元素）**不需要解释**，看一眼就知道 —— 这也是"可感知性 ≥ 强度"（六次修订）在造型层的推论。
- ★ **买了必须有回响，而且要在"能被看见的地方"响三次**：商店里当场响（成就飘字 + 金币到账）、
  结算面板再确认一次（`造型 N / 24`）、成就页长期记录。
  **只在数据里变一次是不够的 —— 没被看见的变化等于没有发生。**

**④ 两个必须守的会计细节（都是"写了才知道"的）：**

- **`career.skinsOwned` 是 career 里唯一不由"一局"产出的字段**（它是商店里发生的事）。
  所以它在**三个时刻**被显式写入：进商城页时对齐、买完当场写、每局结算时写
  —— 而且结算那一次必须排在 `Skins.repairOwned()` **之后**，
  否则老存档里的"幽灵造型"会让计数偏大、把成就提前发出去。
- **`Achievements.evaluate(career, unlocked, onlyFields)` 的第三个参数**。
  它默认"把所有待发的成就一次性结清"（那是**局末**该做的事）。
  商店必须传 `COLLECTION_FIELDS` 只结清收集组 —— 否则买一款造型会顺手把玩法成就也发掉，
  而商店的飘字只报得出 `list[0]` 的名字：**说的和给的对不上**
  （写这一轮的测试时踩到的，飘字说"成就「马拉松」奖励 +300"，发的其实是 6 条成就的总和）。

**⑤ 顺手抓到的一处真缺陷：新手的第一次消费，买回一个和自己一样的东西。**

新加的那条自检（"24 款造型的**完整视觉签名**两两不同"）第一个抓出来的就是它：
**苔痕（180 金币，新手第一款买得起的）** 原来是 `round` + 无拖尾 + 无光效，
而**免费的初心也是** `round` + 无拖尾 + 无光效 —— 两者完整签名完全相同，只差两个绿。

> "没有购买吸引力"这件事，**最锋利的一刀恰恰砍在最该成交的那一次上。**
> 现在苔痕是 `blob`（不规则有机形）+ `ghost`（淡残影）——"一直在长"的东西不该是个规规矩矩的圆。

**⑥ 范围冻结有没有被突破？没有。**

`skinsOwned` 是 career 多**一个字段**，成就是成就表多**三行数据**，
商城改动全在 `shop-scene.js` / `ui.js` / `skins.js` 的表现层。
**没有新增云函数、没有新增数据库集合、没有新增页面**（详情弹层是页内浮层，不是新场景）。
服务端 `submitScore` 一行没改 —— 造型不参与计分。

**⑦ 这一轮最值得记的一句话：**

> **玩家在掏钱之前，必须见过他要买的东西。**
> 舍不得演示，就别指望成交 —— 而"舍不得"往往不是审美问题，是没意识到
> **商店的职责是让人想要，不是让人看见系统里存在这个条目。**

**⑧ 工程上多了一条检查（被一个真实的坑换来的）：`check-scaffold` 的「注释吞代码」。**

一个块注释少写 `*/`，会**静默吞掉几十行之后的代码**（那下面另一个注释的 `*/` 把它收掉了）。
`node --check` 看不出来（未闭合注释不是语法错误）、require 路径检查也看不出来
（它扫的是剥掉注释后的源码，被吞掉的 require 根本不在里面），
直到运行时才炸出一句 `Storage is not defined`，而行号还是准的、源码位置也是对的。
判据只能选"**从注释里开始且顶格的代码行**"—— 换成"原文与剥注释后的 require 数量不等"
会把文档注释里的示例（`subpackages/play/index.js` 就是这么写的）判成违规，
**而会误报的检查等于废的。**

### 🔄 八次修订（2026-10-03）：**把文字做成界面** —— 排版与图形语言层

用户反馈一条："**现在最后就是需要改进这个页面的细节，风格什么的，好多都是单一的文字显示，
文字带给用户体验也很重要，然后整体美化一下，专业一点。**"

这条反馈给的是一个**现象**（"好多都是单一的文字显示"），要先把现象翻译成**原因**，
否则很容易走到错的方向上去 —— 最自然的错误反应是"换个更好看的字体"。

**① 诊断：缺的从来不是字体，是文字周边的东西。**

回头逐页看，全作文字的写法几乎都是同一句：
**把 `fillText` 摆在一个坐标上，然后靠字号大小来表达"这行更重要"。**
于是每一屏都像**一段说明文字** —— 因为它本来就是一串说明文字，只是换了几种字号。
真正缺的是七样东西：**区块标题、图标、分隔线、单位、空状态、加载指示、头像**。
一句话：**页面靠字号表意，而不靠层级。**

**② 解法：`ui.js` 里另开一节「排版与图形语言」。**

它是**纯绘制**的，**不认识任何业务概念**（`framework` 不该知道什么是"稀有度 / 模式 / 成就 / 榜单"）——
这是分层纪律在本轮最直接的兑现：工具集只知道"标题""图标""指标""空状态"，
由场景层去决定"这里该放哪一个"。

| 原语 | 解决的问题 |
|---|---|
| `measure` / `fitText` / `ellipsis` | 量字三件套。⚠️ **canvas 的 `font` 是全局态，量完必须还回去** —— 否则"量出来的宽"和"画出来的宽"会差一个字体，只在个别机型偶尔出现，极难查 |
| `section` | 左竖条 + 标题 + 右附注 —— **五个页面标题同一套语气**，玩家不用读字就知道在哪一页 |
| `stat` | 图标 / 数值 / 单位 / 标签 四层 |
| `kv` | 键值行 + 点线引导 |
| `badge` | 统一角标语言（榜单的「我」与签到格的「大奖」共用） |
| `empty` | 图标 + 主文案 + **下一步该做什么**（一句孤零零的灰字会让人以为页面坏了） |
| `spinner` | "在动"本身就是信息 —— 静态三个字分不清"在加载"和"卡住了" |
| `icon` | **14 个矢量图标**、笔画式（`lineWidth` 随 size 走），同一份代码在 18px 与 92px 下都成立 |
| `monogram` | 字母头像，**色相由昵称哈希决定** ⇒ 同一个名字永远是同一个颜色；零美术资源、零服务端字段 |

`TYPE` 字阶从 6 档扩到 **8 档**（新增 `eyebrow: 20` 区块行标 / `micro: 17` 角标）。

**③ 三条设计判断（这一轮真正想清楚的）：**

- ★ **"数字语言"必须统一：数值大、单位小，而且两个一起居中。**
  各自居中会让一排数字左右不齐 —— **"那一点点差异就是没做完的来源"**。
  应用于：主页最高分、排行榜分数、连签天数、结算分数、金币奖励、购买差额。
  一个 120px 的裸数字，玩家要自己想它是分数、金币还是名次。
- ★ **一组信息要长得像一组。** 三处结构升级都是这一条：
  三个同属一份进度的数字**从三张独立小卡并成一条指标栏**（共用一张底 + 两条竖分隔线，
  分隔线同时表达"这是三个独立指标"与"它们同属一组"）；
  主页"下一款皮肤"**从一行文字变成带进度的小卡**（左边画下一款的 `sprite()` 小预览 ——
  **目标如果只是一个名字，动力会少一半**）；
  排行榜**从一串裸文字变成卡片行**（榜单的信息结构天生是**表格**，
  而表格的可读性 100% 来自对齐、分隔与身份识别；**左对齐的数字列比不出大小**）。
- ★ **一律不用字体字符当图形。** 主页签到卡的右箭头原来是一个 `'›'`。
  字体字符的字重、基线、左右边距**逐机型不同** ——
  这正是"在开发机上好好的、在别人手机上歪了"的典型来源。换成两条 `lineTo`。

**④ 顺手补上一处"真机有、预览页没有"：排行榜镜像。**

排行榜此前是**唯一**一个在浏览器预览版里点进去只弹一句 toast 的画面
（"预览页没有镜像排行榜画面"）—— 而这一轮它刚好是**改动最大**的一页。
所以顺便把它的镜像补齐：假数据榜、会把自己插进去、分数取存档里经典模式的最高分，
还能切到"好友榜"看空状态。**预览页是"验收改动最快的方式"，它缺一页，那一页的改动就等于看不见。**
侧栏从 4 个画面变 5 个。

**⑤ 工程上确立了一条新纪律：新断言必须做一次「注入验证」。**

上一轮是"**会误报的检查等于废的**"（因为一条正则把文档注释判成了违规）。
这一轮补上它的镜像 —— **恒绿的检查同样是废的**。

② 只给真机 `ICONS` 加一个没 `case` 的名字 —— 然后确认检查**真的红了**，最后必定还原。

四条注入全部按预期生效，新断言才算可信。**这一步只花了几分钟，但它区分了"检查写了"和"检查有用"。**

> ⚠️ 顺带记一个坑：`check-preview` 里的 `listBlock(src, name)` **自己会拼** `'const ' + name + ' = ['`，
> 所以传参必须只给**名字**（`'ICONS'`）。传成 `'const ICONS = ['` 会拼出 `const const ICONS = [ = [`，

**⑥ 范围冻结有没有被突破？没有。**

改动全在**表现层**：`ui.js` 加一节纯绘制函数 + 六个场景改造 + 预览页镜像。
**没有新增云函数 / 没有新增数据库集合 / 没有新增页面**
（排行榜本来就是六场景之一，只是预览页此前没镜像它）。
**服务端一行没改。**

> 📌 这一节顺便验证了"越界判据"的两个问题：① 要不要新增云函数/集合/页面？**否。**
> ② 会不会引入需要持续运营的节奏？**否**（排版层是**一次性做完、之后不需要你管**的系统）。
> 两个都否 ⇒ 属于**表现层**，允许迭代。

**⑦ 这一轮最值得记的一句话：**

> **"专业感"从来不来自特效，而来自层级。**
> 用户说"好多都是单一的文字显示"，他抱怨的不是字，是**每一行字都站在同一层上** ——
> 没有标题压在上面、没有图标钉在旁边、没有单位跟在后面、没有分隔线把它和别的分组开。
> 把层级补上，界面立刻像"被设计过"；**加特效只会让它更花，不会让它更专业。**

### 🔄 九次修订（2026-10-03）：**重叠与单调，是两件不同的事**

第八次修订之后，反馈来了两句：**"页面有很多重叠内容啊，文字重叠什么的"** +
**"整个页面黑色有点单调"**。这两句看起来都是"不好看"，但根因完全无关，
**必须分开处理** —— 一起处理就会变成"又加了一堆装饰"。

**① "文字重叠"：先做工具，再改代码。**

重叠是**几何问题**，靠读源码是看不出来的 —— 一个坐标摆在 `safeTop + 372`、
另一个摆在 `+376`，差 4 像素在代码里毫无异常，在屏幕上就是两行字压在一起。
所以先写了一套探针（`_overlap.js` / `_overlap-preview.js`，共用底座 `_ovlib.js`）：
把每次 `fillText` 的坐标 / 字号 / 对齐 / 透明度 / **调用行号**全记下来，
算出真实矩形再两两求交，报出"哪两段字、在哪个坐标、是哪一行代码画的"。

**它抓到的第一个真 bug，是这一轮最有价值的发现：**

> **`ui.text()` 的宽度是在 `ctx.restore()` 之后量的。**
> canvas 的 `font` 是**全局态**，`restore()` 之后它已经变回调用前的字体 ——
> 拿那个字体去 `measureText`，量出来的宽度与刚画出来的那行字不是一个字号。
> 而全作所有"文字 A 的右边接文字 B"的布局都吃这个返回值
> （最典型的是"数值 + 单位"一起居中），于是签到页的「天」直接压在了大数字上。

它可怕的地方在于**不像 bug**：返回值是个正常数字，不报错、不抛异常，只是"差一点"；
更麻烦的是差多少取决于"上一个 `ui.text` 用了多大的字"—— 今天看着好，明天换个数据就歪了。
修法只有一行（把 `measureText` 挪到 `restore` 之前），但**加了一条断言专门盯它**
（`check-preview` 里确认 `measureText` 在源码里出现在 `restore` 之前），否则下次还会被挪回去。

**② 探针的一半工作量花在"消除假阳性"上。**

一个报不出问题的检测器和没问题的项目长得一模一样，**但一个总在误报的检测器更糟**
—— 它会让"真问题"埋进噪音里。四层排除全是被假结论逼出来的：

| 假结论 | 真原因 |
|---|---|
| Boot / Game 报"0 个文字块" | 打桩把 `save/restore` 写成 noop → `ui.sprite({glow:true})` 的 `globalAlpha` 泄漏到整页 |
| 商城"卡片名压在返回按钮上" | 没模拟 `clip()` —— 内容区被裁在 y≤1414，那行字画在 1465，玩家永远看不见 |
| 弹层打开的 4 处"重叠" | 没算遮挡 —— 76% 遮罩 + 不透明弹层卡片叠加后才真的盖住 |
| 同一处重叠报 9 次 / 上千次 | 渲染了多帧，同一段文字被记了很多份 |
| Home 报"整页文字都过淡" | 只跑了 3 帧，入场淡入动画才走到 5% |

**其中有一条判断被推翻了两次，值得单独记：**
"被盖住"最初按"某一层 alpha ≥ 0.55"判定，于是把准备态/结算态判成了"看不见"。
但 **74% 遮罩下的 92px 白字仍然以 26% 透出来，在近黑背景上是明显可见的一层灰白字** ——
它与卡片内容混在一起，恰恰就是玩家嘴里的"文字重叠"。
真正的"看不见"是**叠加**出来的（1 − Π(1−a) ≥ 0.92）。
这个模型改对之后，注入验证才真正通过。

**③ 准备态与结算态的 HUD：两套话在打架。**

`renderHUD()` 此前是"无条件画"，于是：

- **准备态**画了 得分 0 / 0" / 躲避 0 擦身 0 拾取 0，再被 74% 遮罩压住 →
  以 26% 透出来，与开始卡片的模式名、规则速览**混成同一片文字**；
  而且计数行（y=388）与 54px 模式名的下沿（387）在坐标上真的相接。
- **结算态**画了 92px 大分数 + 「得分」标签，而结算面板自己就有 120px 大分数和
  「第 N 局 · 模式」标题 —— **同一个数字被写了两遍**。

改成 `if (state === STATE.PLAYING) renderHUD(ctx);` 一处解决两态。
准备态那些读数**全是初值**，零信息量；命数信息也没丢 ——
规则速览第一行就是机制，而"有 3 条命"由开局后右上角的三格立刻给出。

**④ "黑色单调"：六个页面不该是同一块黑。**

此前六个场景共用一条 `#18202b → #0d131a` 的纵向渐变。单看没问题，
连着切几页就会发现"每页都是同一块黑"，而且**只有明度变化，没有光照方向、没有材质**。

改法刻意选了**零额外填充成本**的那条路（低端机纪律：每帧的像素填充量不该翻倍）：

1. **光晕并进主渐变的色标里**，不另起一层径向渐变 —— 顶部先染一抹该页的主题色
   （`bgTop` 混 24% tint），22% 处回落到中性，底部再压暗一档。
   得到"光从上方来"的观感，成本仍然是**一次全屏 `fillRect`，与改动前完全一样**。
2. **一层 2% 白的网格**（间距 112），十几条 1px `fillRect` ——
   把"平面"变成"有尺度的空间"。2% 是"看得到格子但读不出格子"的那一档。
3. 每页各自的 tint：主页/启动 `brand`、商城/签到 `gold`、排行榜 `accent`、游戏内 `mode.color`。

> **页面之间的差异只应该是色相，不该是光照逻辑** —— 让每页自己画背景，
> 会立刻漂成六套光照方向。这也是为什么 `bg()` 仍然只有一个入口。

顺手补掉一处**镜像遗漏**：预览页的商城还在用 `COLORS.bg` 纯色，
即真机早就改成渐变、预览页没跟上 —— 它一个人纯色，六页里就有一页明显比别的平。
（`check-preview` 现在有一条断言：预览页不允许存在"还在用纯色背景"的页面。）

**⑤ 还有一类"重叠"是字面意义上的：同屏信息说两遍。**

商城页头部写 `已拥有 6 / 24`、同一行右端又写 `4%`、页签上还写着 `皮肤 6/24` ——
同一件事说了三遍。现在的分工是：**进度条自己说明比例、右端百分比说明进度、
页签上的数字说明"这个列表有多少"**，头部只留一个「收集进度」的标签。

> **判据：任何一个数字，在一屏里只该有一个家。**
> 出现第二个"家"时，先问它是不是在回答另一个问题；不是就删掉。

**⑥ 范围冻结自检（沿用 §一 的两个判据）：**
① 有没有新增云函数 / 集合 / 页面？—— **零**。
② 有没有引入需要持续运营的节奏？—— **零**。
改的全部是"同一批元素怎么摆、背景什么色"，**服务端一行没改**，
`config.GAME` 的数值一个没动。

**⑦ 这一轮最值得记的一句话：**

> **先做工具，再改代码；而工具的头号指标不是"能发现问题"，是"报出来的都是真的"。**
> 这一轮在"消除假阳性"上花的时间，比在修布局上花的多 ——
> 但正是这些时间，让最后那句"全场景 0 处重叠"是**可信的**，而不是"检查没报"。

### 🔄 十次修订（2026-10-04）：**"字体重合"的第二半 —— 文字被图形的边切掉**

九次修订把"重叠"当成"文字 ↔ 文字"来查，于是**漏掉了一半**。玩家紧接着的反馈是
**"有些字体重合了看不清"** —— 这句话把范围指得更准了：不是"挤"，是"看不清"。

**① 先承认漏判：探针当时报"0 处重叠"，与玩家看到的对不上。**
按纪律不能靠读代码反驳它，于是改用 headless Chrome 把预览页逐屏截下来**看真实像素**。
（顺带沉淀三个小工具：`_mkshots.py` 生成"指定画面/状态"的临时副本、`_shoot.sh` 截图、
`_crop.py` 按设计坐标裁剪 —— 设计坐标 → 图像坐标 = `(196+2x, 280+2y)`。）

**② 找到了漏判的那一类：卡片/药丸这类"图形"的边缘，切在文字上。**
商城头部的「装扮 · 成就」被金色药丸切掉最后两个字。它躲过文字↔文字判定有两个原因：
药丸是**图形**；而且药丸画在文字**之后**（是它压住了字，不是字压住了它）。
⇒ 补一条独立的判定 **「压边」**：文字盒与实心块（含**描边** —— 真正切字的正是那条金线）
**部分相交**才算。三条约束把噪音从 15+ 压到 0：
① 块必须画在文字**之后**；② 压掉的必须是一条**实质的带**（≥ 半个字高）；
③ 每条文字只取**包含比最大**的那个块（卡里还套着预览底板/顶部高光，逐块比对会刷屏）。

**③ 它又抓出两个真 bug —— 而且两个都不是"调参"能修的，是几何依赖没建立：**

| 位置 | 原来是 | 根因 | 现在 |
|---|---|---|---|
| 商城头部标题 | `w: screen.width - 200` | 药丸宽度 `max(146, 数字宽+52)` **随金币位数变化**；0 金币时药丸左边缘 556、附注右端 598 ⇒ 切 42px | `w: pillX - 24 - 48` |
| 签到浮层卡片 | `w = 500` | 日历 4×160+3×16 = 688 宽也居中 ⇒ 最左格切 37px、最右格切 28px | `w = screen.width - 96` |

> ⚠️ **差点走偏的一次判断：我第一反应是"把遮罩调黑"。**
> 因为看起来是"背景字太亮所以抢注意力"。实际做了 0.34 → 0.62 的改动并**截图对比**，
> 发现背景只是**略微**变暗，**切字这件事一点没变** —— 调黑只是让问题看不见，
> 而且换个奖励数值（字更宽）照样会露。
> **调参治不了碰撞，让几何建立依赖才行。** 于是撤掉遮罩改动，改成让宽度真正依赖相邻元素。

**④ 顺带修掉两个"不像 bug"的错误：**
- 商城弹层主按钮写着 **「还差 undefined 金币」** —— 代码取 `st.left`，而数据里给的字段是 `st.text`。
  （`undefined` 不会抛异常，只会安静地画在按钮上。）
- 签到浮层卡片原来是 **96% 不透明**（不是实心），那 4% 足够让背后日历透成一层灰影。

**⑤ 验证方式也升级了：探针的注入验证从 2 条扩到 4 条。**
`_inject-overlap.js` 把四个真 bug 重新造出来（`ui.text` 宽度时机 / HUD 门控 /
商城头部宽度 / 签到浮层宽度），确认探针**真会红**：**15/15 通过**，四个文件逐字节还原。
另外 `check-preview` 新增 4 条**源码级**几何契约断言（80 → **84**），也做了一次注入验证
（改回旧写法 → 2 条 FAIL → 还原 → 84 全绿）。

**⑥ 范围冻结自检：** ① 新增云函数 / 集合 / 页面？—— **零**。
② 引入需要持续运营的节奏？—— **零**。
改的是两个场景文件 + 预览页镜像 + 测试与文档，**服务端一行没改**。

> **这一轮的判断修正（写下来免得下次又走一遍）：**
> 1. 「重叠」必须分成**两类**看：文字↔文字（挤）与**图形边缘切文字**（切）。
>    只做前者的检测器，对玩家最常说的"看不清"是瞎的。
> 2. 「加宽 / 缩短 / 调暗」这类**数值修补**只能掩盖碰撞；
>    碰撞的根因是**几何依赖没建立**（写死了一个"大概够"的数字）。
> 3. 还有一个**方法论上的副产品**：读图工具会按内容哈希去重，
>    所以"看起来没变"未必是真的没变 —— 判断改动是否生效要**量化**（取像素均值/最亮值），
>    或者输出到全新文件名再读。

### 🔄 十一次修订（2026-10-04 下午）：**阈值造出来的假绿 —— 探针说"0 处重叠"，玩家说"字重合了"**

十次修订之后，八套自检全绿、探针写着"合计 0 处重叠"。然后玩家贴了一张**真机截图**：
三张统计卡里，「4 天」的**"天"压在「累计签到」上**，"/24"贴着「皮肤」，"/19"贴着「成就」。

**① 这一轮最值钱的不是那条修复，是"探针为什么会漏"。**

漏的是**阈值造的假绿**。判定要求"交集占到较小那个的 25% 宽 / 35% 高"才算重叠 ——
这条阈值本身没错（它是为了压掉"相邻两行"这种正常排版），但它顺手挖出一个**盲区**：
两段文字只压进去 3~4px 时，**既不算"重叠"、也不算"过挤"**（过挤那条只查**没**相交的），
于是从报告里静默消失。

**② 根因在 `ui.stat` 的纵向排布，是两个魔数比例。**

| 位置 | 原来是 | 根因 | 现在 |
|---|---|---|---|
| 统计卡三层 | `valueCy = o.y + o.h * 0.60`、`labelCy = o.y + o.h - 16` | "数值"的下沿**不是数值基线**：单位要下沉 `vs×0.28` 再算自己的半高，整块往下探了 ≈19.5px ⇒ 单位与标签的**墨迹恰好相切**。h=100 时上下净空各只剩 4px | 三层**自上而下流式排布**（量高度 → 按 6px 最小净空排 → 整体居中）；`L.stats.h` 100 → 108 |

这与九/十次修订的两次是**同一个道理**：**一个元素的位置取决于另一个元素的"实际尺寸"，
就不能各算各的。**（药丸宽度 vs 附注收边 / 卡片宽度 vs 日历宽度 / 数值块高度 vs 标签位置。）

**③ 探针改了两件事，缺一不可：**

- **把尺子从"盒子"换成"墨迹盒"。** 盒子是按字号给的正方形，而笔画没那么高 ——
  20px 西文数字墨迹约 14px（盒子多留 3px），120px 大数字多留 17px。
  所以"盒相交 4px"在小字上是"糊在一起"、在大字上什么都不是。
  拿盒子当尺子，阈值只能二选一：**小字漏报，或大字误报** —— 而**两件事都发生过**
  （小字漏报＝本轮统计卡；大字误报＝结算面板 120px 的「95」被误报成贴死「新纪录!」，
  实际墨迹之间还有 10px 空，换成墨迹盒后自动消失）。
- **单列一类「贴死」并计入总计。** 墨迹相交不足 35%、或只相隔 2.5px 以内的组合单列出来，
  并且**算进最后那句"N 处文字相撞"** —— 否则报告末尾那句话又会变成假话，
  而它恰恰是把玩家反馈挡在门外的那句话。

**④ 注入验证扩到 5 条，19/19 通过。** 新增的第 ⑤ 条把"魔数排布 + h=100"一起改回去
（**必须两处一起改**才复现 —— 流式排布本身在 h=100 下也能自洽排开），

### 🔄 十二次修订（2026-10-04 傍晚）：**判定类型不够 + 场景没铺满，也是假绿**

十一次修订刚把"阈值造的假绿"堵上，玩家又贴来**两张真机截图**："这里也有问题"。
两端探针当时都写着"**0 处文字相撞**"。两个缺陷：

| # | 位置 | 症状 | 探针为什么没报 |
|---|---|---|---|
| ① | 签到页 ·「累计里程碑」标题 | 30px 标题墨迹**扎进日历最后一排格子 7px** | 「压边」要求"块画在文字**之后**"；日历格子画在标题**之前**。而且格子不是文字，文字↔文字那条也求不出交 |
| ② | 金潮 · READY 面板规则行 | 「★ 金块会横向游走…」35 字 @25px ≈ 870px，卡片只有 632px，真机左右各溢出 52px+ | READY 面板**按模式渲染**，而探针只测了默认的经典模式 ⇒ **覆盖面不够的 0** |

**① 这一轮的产出仍然是"判定类别"，不是那两行代码。** 新增两类：

- **「越界」`outbound`** —— 文字捅出**它所属容器**的左右边界（超出 > 3px 才算）。容器 = 文字中心
  落在其内 + 画在文字**之前** + 面积 ≥ 1.2 倍字 + 宽 ≥ **半屏** + 由**路径填充**画出的矩形里
  **面积最小**的那个。（半屏门槛是两次假阳性逼出来的：皮肤详情「苔痕」曾越出预览光晕 8px / 70px。）
- **「压块」`block`** —— 文字跨在一个**实心块**的边界上（中心**不在**块内）。四条约束把噪音压到零：
  ① 块画在文字**之前**；② **同一屏幕层**；③ 横向重叠 ≥ 40% 字宽；④ 纵向 ≥ 4px 且 ≥ 25% 墨迹高、
  相交比 < 0.8，且中间无 ≥ 0.8 不透明填充遮挡。

> ★★ **「同一屏幕层」是防假阳性的关键。** 每次全屏级 `fillRect`（w≥600 且 h≥700）令 `state.layer++`。
> 有了它才能把"浮层遮挡背景"（**跨**层，正常）与"同区块内图形切字"（**同**层，真问题）分开 ——
> 否则签到浮层卡片的背景会把每一条它盖住的字都刷成"压块"。

**② 两处修复，又都是"几何依赖没建立"：**

| 位置 | 原来是 | 根因 | 现在 |
|---|---|---|---|
| 签到页区块间距 | `CAL_DY = 400`、`MILE_DY = 762`（都写死） | 日历实际高 316，从 400 排到底 = 716，里程碑却从 762 起 ⇒ 净空只剩约 4px | `MILE_DY = CAL_DY + CAL_H + SECTION_DROP + 11 + SECTION_GAP`（从**日历实际下沿**推出）；规则卡 `ruleCardY()` 取"顶部流 vs 底部锚定"更靠下者，保矮屏不撞 |
| READY 规则行 | `const segs = [modeRuleText[i]]`（整行当一段） | 文案派生自参数、长度不可控；既不能缩字号（读不动）也不能截断（切掉关键信息） | 新增 `ui.wrapText()` **按宽度折行**（中文按字断、气口优先）；卡片高度由**实测行数**决定，药丸宽度改用 `ui.measure()` 而非 `length*22` |

**③ 探针自己也在几何上栽过一次：** `intersect(a, b)` 原来只返回 `{w, h}`，于是 `coveredBetween()`
里拿 `q.l / q.r` 全算出 `NaN`，"中间有没有遮挡"**永远判不出** —— 不报错、不抛异常，只是这条约束静默失效。
改成返回完整矩形 `{l,t,r,b,w,h}` 才生效。**又一次印证那句话：不报，不等于没事。**

**④ 场景按维度展开：** READY 面板按模式渲染 ⇒ 探针**必须跑四个模式**；真机探针从

否则局部坐标混进设计坐标系会造成"假相交"。

## 五、这个作品在技术评审里怎么讲

**一句话定位（别背，理解就行）：**

> 独立设计并上线了一款微信小游戏：自研轻量 Canvas 框架 + 微信云开发后端，完整走通了从架构设计、服务端防作弊到软著备案上线的全流程。

**八个可以展开的技术点（评审时容易被追问的）：**

1. **为什么不用现成引擎？** 休闲小游戏体量小，自研分层框架能做到零构建、包体最小；讲清 `scenes → platform → framework` 的单向依赖为什么能隔离平台差异。
2. **主循环怎么做才不掉帧？** 定步长 `1/60` 推进物理 + 插值渲染，保证 60Hz 与 30Hz 设备上速度一致；切后台必须 `pause()`，回前台做补帧。
3. **怎么防作弊？** 客户端 JS 对用户完全可见，所以**分数一律不可信** —— 服务端四道校验：时长上下限、每秒分数上限、提交频率、增量合理性。**加分版**：四个模式的每秒上限各不相同，且这个上限**不是手填的**，而是从该模式的实际参数推导出来的（`rateOf`），改了玩法参数就自动跟上 —— 并且有测试逐值比对本机推导与云端常量表。
4. **多设备存档怎么不互相覆盖？** 本地实时写 → 关键节点异步上云 → 云端 `version` 乐观锁做冲突合并。**加分版**：存档版本 `v1→v4` 每升一级都只加字段、不删字段，旧版本读上来先走一次 `normalize()`，所以玩家的老存档不会因为一次改动变成 `NaN`。
5. **平台能力怎么封装？** 只有 platform 层允许碰 `wx.*`，业务层不感知平台；云函数统一返回 `{ code, data }`。
6. **"设计"是怎么落到代码里的？** 拿"三个独有机制"讲：模式不是靠调数值区分（玩家体感是"只是快慢不同"），而是每个模式各开一条**彼此正交**的机制，并且**每条都必须是玩家看得见的运动**（障碍的摆动轨迹带 / 金块的运动残影 / 走廊墙面的拖影）—— **可感知性 ≠ 强度**。更能讲的是它的实现代价：机制以 `config.GAME` 里几个**默认关闭的开关**存在，关闭时行为与原实现逐字节一致，所以四个模式共用同一套规则代码，加第五个模式的成本接近零。
7. **界面是怎么做到"专业"的？** 拿"排版与图形语言层"讲：先诊断出"界面不像被设计过"的根因**不是字体，而是文字全都站在同一层级上**；于是补的是结构（区块标题 / 图标 / 单位 / 分隔线 / 空状态），并且把"层级"写成可复用的原语而不是逐处手写。**最值钱的一句是**：整层是**纯绘制、不认识任何业务概念**的（它不知道什么是"稀有度/模式/榜单"）—— 这正是分层纪律在表现层的兑现，也是评审时能一下说清的"边界感"。
8. **上线流程本身** —— 软著登记、工信部备案、适龄提示、隐私合规。这条证明的是"**能把产品做上线**"，而不只是"会写代码"，恰恰是最容易被忽略的一条。

**加分动作**：把代码开源到 GitHub 作为可展示产出（仓库里已连好 GitHub）。评审时能给链接，比嘴上说强得多。
